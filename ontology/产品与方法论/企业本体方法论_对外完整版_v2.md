# 企业本体方法论

> **从业务问题到可运营、可复用、可审计的企业语义资产**

**版本：2.0（对外完整版）**  
**适用对象：** 企业管理者、业务负责人、数据与 AI 负责人、企业架构师、本体架构师、数据治理团队、产品与交付团队  
**文档目的：** 说明企业为什么需要本体、什么场景值得建设、如何从一个业务场景完成建模与认证、如何进入生产运营，以及如何通过组织治理和产品化机制持续产生业务价值。

---

## 阅读说明

企业本体不是一张静态的概念图，也不是知识图谱、数据模型、数据目录或主数据管理的同义词。它是一套以**业务对象、关系、事件、状态、规则、指标与动作**为核心的企业语义模型，并通过数据映射、质量控制、权限、版本、运行监控和组织责任，将分散在业务系统、数据平台、文档和人员经验中的知识，转化为可查询、可组合、可执行、可追溯和可治理的企业资产。

本方法论重点回答六个问题：

1. 什么业务问题适合使用企业本体，什么问题应优先采用其他方案；
2. 如何从业务场景、数据、文档和代码中发现并建设本体；
3. 如何对本体相关的数据、证据、身份、时间和质量进行治理；
4. 如何让候选模型经过认证，成为可被组织信任的正式资产；
5. 如何把认证本体接入业务流程、应用与 AI Agent，并安全进入生产；
6. 如何建立长期组织、运营和价值实现机制，使本体从一次性项目转变为企业能力。

为避免将建议写成不加区分的“统一标准”，全文使用四类标记：

- **强制原则**：缺失后将直接破坏可信性、安全性或可运营性，原则上必须遵守；
- **默认建议**：适用于多数企业，但可以根据已有架构和场景条件调整；
- **可选模式**：不同模式各有适用条件，需要通过架构决策选择；
- **示例参数**：用于帮助理解，不应直接作为所有企业的统一阈值、时限或权重。

## 执行摘要

### 一、企业本体解决的不是“缺一张图”，而是“企业无法稳定表达和执行复杂业务判断”

当企业遇到以下问题时，单纯增加报表、接口或字段通常不能从根本上解决：

- 同一“客户、供应商、订单、合同、设备、状态”在不同部门或系统中含义不一致；
- 一个关键判断需要跨多个对象、多个时间点和多个数据口径才能完成；
- 业务事实虽然存在于系统中，但无法解释其来源、变化过程和责任主体；
- 规则、例外和专家经验分散在代码、制度、文档和人员脑中，无法被稳定复用；
- AI 能够生成文本，却无法可靠获得对象级上下文、调用受控动作或留下完整审计记录；
- 企业希望在不重建全部业务系统的前提下，增加一层统一的业务语义与行动控制能力。

企业本体的作用，是把这些分散的信息重新组织为一套可治理的对象和关系体系，并将其连接到真实数据、业务规则、应用接口和行动权限。它不替代 ERP、CRM、MES、数据仓库或主数据系统，而是在这些系统之上建立统一的**业务语义与对象控制层**。

### 二、候选、认证、生产是同一项本体资产的三个生命周期状态

企业本体项目不应把“模型已经生成”视为完成。一个本体需要依次经历三个状态：

| 生命周期状态 | 定义 | 主要资产包 | 进入下一状态的条件 |
| --- | --- | --- | --- |
| **候选状态** | 从业务材料、数据、代码和专家访谈中发现的模型草案 | 候选模型、证据记录、能力问题覆盖矩阵、数据映射草案、待确认问题 | 关键元素有来源或明确设计依据，结构校验通过，可进入正式评审 |
| **认证状态** | 经业务、数据和架构评审，形成正式语义契约的可信模型 | 认证模型、语义契约、评审记录、质量报告、版本说明、消费者确认 | 业务语义明确、数据可支撑、兼容性与风险可接受、发布条件满足 |
| **生产状态** | 已与真实数据、应用和业务流程连接，并具备监控、回滚和运营责任的运行资产 | 已部署模型、运行映射、权限策略、监控指标、运营手册、回滚方案 | 持续通过生产质量闸门，并能够稳定支撑业务结果 |

这不是三套彼此独立的本体，而是同一资产从“被发现”到“被组织认可”，再到“被生产系统安全使用”的三个成熟度状态。

### 三、完整方法不是“先建一个企业级大本体”，而是从一个可验证的业务场景开始

本方法论采用以下主线：

```text
业务问题与价值假设
        ↓
场景章程、能力问题与范围
        ↓
数据盘点、证据管理与准备度评估
        ↓
候选本体发现、设计与映射
        ↓
语义认证、质量验证与发布准备
        ↓
历史回放、影子运行与渐进放权
        ↓
生产运营、价值衡量与持续治理
        ↓
模板化、跨场景复用与规模化
```

起点必须是一个有业务负责人、有决策后果、有可验证指标的具体场景，而不是“建设一个覆盖全公司的本体平台”。企业级本体应通过多个经过验证的领域场景逐步汇聚，而不是一次性自上而下设计完成。

### 四、贯穿全生命周期的三条底线

1. **无来源或设计依据，不进入正式资产。** 每个对象、关系、规则、动作和关键属性，都必须标记为“来源证据”或“显式设计决策”，并记录责任人、时间和适用范围。
2. **未通过验证，不进入下一状态。** 候选、认证和生产状态分别设置结构、语义、数据、兼容性、安全和运行质量闸门。
3. **无决策记录，不完成治理闭环。** 专家对候选模型的接受、修改、合并、拆分、否决或搁置，必须记录结论、理由、证据和影响，形成可复用的组织知识。

## 第一部分：认识企业本体与总体方法

### 第 1 章 企业本体的定义、边界与适用范围

#### 1.1 企业本体的正式定义

企业本体是一套对企业业务世界进行明确表达的语义模型。它定义企业关心的业务对象是什么、对象之间如何关联、事实在什么时间有效、对象如何变化、哪些规则约束业务、哪些指标用于判断、哪些动作可以被谁在什么条件下执行。

一个可进入生产的企业本体通常包含五个相互连接的层次：

1. **模型层**：对象类型、属性、关系、事件、状态、规则、指标、动作和约束；
2. **实例层**：具体的供应商、合同、订单、设备、组织、人员和交易事实；
3. **映射层**：模型元素如何映射到数据库、API、消息、文档、代码和主数据；
4. **执行层**：对象如何被查询、组合、审批、写回、调用工具或触发业务动作；
5. **治理层**：版本、证据、质量、权限、责任、审计、生命周期和价值指标。

只有模型层而没有真实数据映射，本体只是概念模型；只有实例图而没有正式语义和治理，本体只是数据关联；只有动作接口而没有权限与审计，则无法安全进入生产。企业本体的完整价值来自五层协同。

#### 1.2 企业本体与相邻能力的区别

| 能力 | 主要回答的问题 | 与企业本体的关系 |
| --- | --- | --- |
| **概念数据模型** | 数据实体和字段如何组织 | 是本体设计的重要输入，但通常不覆盖业务规则、事件、动作、证据和治理 |
| **知识图谱** | 具体实体及其关系如何连接 | 可以作为本体实例的实现方式之一；知识图谱强调数据连接，本体强调正式语义与约束 |
| **语义层** | 指标、维度和查询口径如何统一 | 通常聚焦分析消费；企业本体还覆盖运营对象、状态、事件、动作和写回 |
| **主数据管理** | 客户、供应商、物料等核心对象如何统一身份和权威值 | 为本体提供可信身份与属性；本体进一步表达跨域关系、业务语义和行动能力 |
| **数据目录** | 企业有哪些数据、由谁负责、如何发现 | 为本体提供数据资产、责任和血缘信息；本体把数据映射到业务对象与决策场景 |
| **流程模型** | 业务活动按什么顺序执行 | 本体表达流程涉及的对象、状态、事件、规则和动作，两者可以结合 |
| **API 与集成平台** | 系统之间如何传递数据和调用功能 | 提供连接能力；本体提供统一的对象语义、动作含义和调用约束 |
| **业务规则引擎** | 确定性规则如何执行 | 可成为本体执行层的一部分；本体负责规则所引用对象和语义的一致性 |

因此，企业本体不是替代上述能力，而是把它们连接到统一的业务语义和对象体系中。

#### 1.3 企业本体适合解决的问题

企业本体通常适合以下类型的问题：

- **跨对象决策**：一个判断需要组合多个业务对象和多跳关系；
- **跨时间追溯**：需要回答某个历史时点的事实、变化过程和当时依据；
- **语义冲突治理**：同一术语、状态或指标在多个场景中含义不同；
- **复杂身份统一**：同一客户、供应商、设备或组织在多个系统中具有不同标识；
- **规则与例外显式化**：业务规则分散在代码、制度和人员经验中；
- **运营级智能化**：AI 或应用需要对象级上下文、受控工具、动作权限和完整审计；
- **跨域复用**：同一核心对象需要被多个场景稳定复用，而不能每个项目重新定义。

#### 1.4 不应优先使用本体的情况

以下问题通常应先考虑更简单的解决方案：

- 单一系统内的简单增删改查、报表或字段补充；
- 业务语义清晰、数据结构稳定，普通数据模型即可满足；
- 主要问题是制度不执行、责任不清或数据录入纪律差，而非表达能力不足；
- 缺少业务负责人、无法获得数据授权、也无法定义验收指标；
- 建设成本显著高于可验证价值，且没有跨场景复用潜力；
- 只是为了采用图数据库、知识图谱或大模型而寻找场景。

但“新业务”本身不是否决条件。对于需要跨域共享语义、长期复用对象、支持多 Agent 协同或从第一天就要求审计与行动治理的绿地平台，本体仍可能是合理的基础能力。

#### 1.5 企业本体的边界

企业本体应明确以下边界：

- 它不替代业务系统的交易处理能力；
- 它不自动修复错误的主数据、计划参数和业务流程；
- 它不保证 AI 不产生错误，但可以缩小语义和行动边界；
- 它不要求所有业务实例都复制到图数据库；
- 它不要求一次性覆盖整个企业；
- 它不是纯技术项目，业务负责人必须对最终业务结果负责。

### 第 2 章 总体方法、生命周期与参考架构

#### 2.1 生命周期总览

本方法论将一个场景从立项到规模化划分为八个阶段：

| 阶段 | 核心问题 | 主要交付物 | 退出条件 |
| --- | --- | --- | --- |
| **S0 场景决策** | 是否值得使用本体 | 场景初筛、替代方案比较、价值假设 | 有业务负责人、问题边界和继续评估的理由 |
| **S1 范围定义** | 具体解决什么、暂时不解决什么 | 场景章程、能力问题、范围与非目标 | 能力问题可测试，边界和责任明确 |
| **S2 数据准备** | 是否有足够可信的数据和证据 | 资产清单、证据目录、数据准备度报告 | 关键数据可访问，主要风险有处理方案 |
| **S3 候选建设** | 业务语义如何被表达 | 候选模型、映射草案、证据包、问题清单 | 关键元素可追溯，结构校验通过 |
| **S4 语义认证** | 模型是否可以被组织正式信任 | 语义契约、评审记录、质量报告、认证版本 | 业务、数据、架构和消费者完成确认 |
| **S5 生产验证** | 在不影响业务的情况下能否证明有效 | 历史回放、影子运行、用户验收、风险报告 | 结果稳定，错误和异常处理机制可接受 |
| **S6 生产运营** | 如何安全支持真实业务 | 部署版本、权限策略、监控、运营手册、回滚方案 | 质量闸门持续满足，责任团队能够运营 |
| **S7 价值扩展** | 如何复制到更多场景和业务域 | 价值报告、复用资产、模板、路线图 | 试点价值被验证，复用边界和投资决策明确 |

各阶段不是一次性瀑布流程。数据问题可能使项目回到范围定义，生产异常可能触发模型修订，新的评审结论也应回流到证据规则、提示模板和评估集。

#### 2.2 六类核心交付包

为避免项目只交付一张模型图，建议按交付包管理资产：

1. **业务场景包**：场景章程、价值假设、基线、能力问题、范围与非目标；
2. **数据与证据包**：资产清单、授权、证据坐标、数据质量、身份和时间规则；
3. **候选本体包**：模型、映射、证据覆盖、置信度、设计决策、待确认问题；
4. **认证本体包**：语义契约、评审记录、自动测试、质量报告、版本与兼容性说明；
5. **生产运营包**：部署配置、访问接口、权限、监控、告警、运行手册、停机与回滚；
6. **价值实现包**：流程变化、采用率、业务指标、价值归因、复用资产和后续路线图。

#### 2.3 参考架构：五层结构

```text
业务与应用层
决策应用｜运营工作台｜分析应用｜AI Agent｜外部服务
                         │
行动与服务层
对象查询｜语义检索｜规则执行｜动作调用｜审批｜写回｜事件订阅
                         │
本体模型层
对象｜属性｜关系｜事件｜状态｜规则｜指标｜动作｜策略
                         │
映射与数据访问层
数据库｜数据湖仓｜主数据｜API｜消息｜文档｜代码｜外部数据
                         │
治理与运行层（横切）
证据｜版本｜质量｜权限｜血缘｜审计｜监控｜责任｜价值指标
```

该结构表达的是职责分层，不要求所有企业采用相同产品。企业可以基于现有数据平台、集成平台、元数据平台、图数据库或 RDF 存储组合实现。

#### 2.4 模型与事实的存储模式

**默认建议：** 将模型元数据和业务实例数据分开治理，但不强制使用同一种物理存储。

##### 模型元数据存储

模型元数据可以存储在图数据库、RDF 存储、关系数据库、文档数据库或专业元数据平台中。选择时重点考虑：

- 是否需要复杂关系查询或语义推理；
- 是否需要成熟的事务、权限和审计能力；
- 是否需要标准化语义表示和互操作；
- 现有团队的运维能力；
- 版本、差异和发布能力是否由平台原生支持。

##### 业务实例数据访问

| 模式 | 做法 | 优点 | 主要风险 | 适用条件 |
| --- | --- | --- | --- | --- |
| **联邦或虚拟访问** | 数据保留在权威源，运行时按映射查询 | 减少复制，保持源系统权威 | 性能、可用性和跨源一致性复杂 | 数据量大、复制受限、源系统接口稳定 |
| **物化实例图** | 将选定对象和关系同步到图或语义存储 | 多跳查询和推理性能好 | 数据同步、时效和重复治理成本高 | 图分析强、低延迟、离线推理或源系统访问受限 |
| **混合模式** | 核心身份和关键关系物化，明细按需联邦 | 在性能与权威源之间平衡 | 架构和一致性管理更复杂 | 大多数企业级复杂场景 |

架构决策应依据查询复杂度、时效、数据规模、合规限制、写回需求、推理需求和现有技术基础，而不是预设“本体必须使用图数据库”。

#### 2.5 质量闸门体系

质量闸门不是一个总分，而是一组针对不同风险的进入条件：

- **业务闸门**：场景、决策、价值和负责人是否明确；
- **语义闸门**：对象、关系、状态、事件、规则和动作是否定义清楚；
- **数据闸门**：关键数据是否可访问、可追溯并达到场景所需质量；
- **结构闸门**：模型是否满足元模型、命名、基数和约束规则；
- **兼容性闸门**：变更是否影响现有消费者，迁移方案是否充分；
- **安全闸门**：权限、隐私、数据使用和动作授权是否合规；
- **运行闸门**：性能、可用性、监控、降级和回滚是否就绪；
- **价值闸门**：试点是否达到预设的业务验收和采用标准。

同一闸门在不同场景中的阈值可以不同，但闸门类别和责任归属必须明确。

## 第二部分：从业务问题到可信模型

### 第 3 章 业务场景（Use Case）选择与价值假设

#### 3.1 目的

本章用于判断一个业务问题是否值得采用本体，以及是否具备成功实施的基本条件。选择场景的关键不是“系统是否足够多”，而是现有业务模型是否能够稳定表达、追溯和支持关键决策。

#### 3.2 先比较替代方案

在决定建设本体前，应至少比较以下选项：

- 修复主数据或参考数据；
- 增加报表、指标或分析模型；
- 增加业务系统模块或接口；
- 优化流程、制度和岗位责任；
- 建设规则引擎或决策服务；
- 建设知识图谱或搜索系统；
- 建设企业本体与对象服务。

本体应当在“业务语义复杂、跨对象关系重要、需要长期复用、需要治理和行动能力”的情况下胜出，而不是因为它听起来更先进。

#### 3.3 典型触发信号

以下信号命中越多，本体的适配度通常越高：

1. **长期反复发生的决策问题**：多次立项、反复补数据或改规则，仍无法稳定解决；
2. **语义口径冲突**：同一对象、状态或指标在不同部门、系统或时间段含义不一致；
3. **穿透式关系与时间追溯**：需要跨多跳关系、多个时间点和多个来源形成完整证据链；
4. **专家判断难以复用**：关键规则和例外依赖少数人的经验；
5. **多个场景重复定义同一对象**：客户、供应商、合同、产品等被反复建模；
6. **应用或 Agent 需要安全行动**：不仅要回答问题，还需要调用动作、审批、写回和审计。

#### 3.4 场景评分卡

评分卡用于结构化讨论，不应机械替代管理判断。建议采用 1—5 分，并根据企业战略调整权重。

| 维度 | 低分特征 | 高分特征 | 建议关注 |
| --- | --- | --- | --- |
| **业务重要性** | 边缘需求，影响有限 | 影响核心收入、成本、交付、风险或监管 | 是否有明确业务负责人 |
| **现有方案不足** | 普通报表或功能即可解决 | 当前模型无法稳定表达或成本不可接受 | 是否真正比较过替代方案 |
| **语义复杂度** | 对象少、口径稳定 | 多对象、多口径、多状态和复杂例外 | 是否需要正式语义契约 |
| **关系与追溯需求** | 单点查询 | 多跳、跨时间、跨来源追溯 | 是否需要证据链和双时态 |
| **复用潜力** | 仅服务单个短期需求 | 核心对象和能力可服务多个场景 | 是否能形成领域资产 |
| **数据准备度** | 数据不可访问或严重缺失 | 关键数据可获得，主要质量问题可治理 | 是否能够在试点周期内解决 |
| **实施可行性** | 缺少人员、平台或权限 | 有业务、数据、架构和交付能力 | 是否存在关键依赖 |
| **风险可控性** | 动作不可逆、合规不明 | 可先回放和影子运行，边界可控 | 是否有安全停机方案 |

##### 决策建议

- **优先试点**：业务价值高、现有方案明显不足、关键数据可获得、负责人明确，且可从低风险模式开始验证；
- **先做准备**：适配度高，但数据、身份、授权或组织能力尚未就绪；
- **采用其他方案**：问题可用更低成本的系统、数据或流程改造解决；
- **暂不实施**：无法定义业务价值、数据不可获得或没有最终负责人。

#### 3.5 价值假设

每个试点必须形成一句可验证的价值假设：

> 通过把【哪些业务对象与关系】建立为可追溯的统一模型，并在【哪个业务环节】提供【查询、判断或动作】，预计将【哪个业务指标】从【当前基线】改善到【目标值】，由【业务负责人】对结果负责。

价值指标应同时覆盖：

- **领先指标**：对象覆盖率、数据可用率、查询调用量、建议采纳率、流程使用率；
- **结果指标**：处理时长、错误率、库存、交付、损失、风险事件、收入或成本；
- **约束指标**：误判率、权限违规、系统延迟、人工复核量、运营成本。

#### 3.6 停止条件

试点开始前必须定义停止条件，例如：

- 关键数据在约定周期内无法获得；
- 业务负责人无法持续参与评审和验收；
- 历史回放无法达到最低准确性或覆盖率；
- 业务流程不愿使用，且没有可执行的采用改进方案；
- 建设和运营成本持续高于可验证价值；
- 发现问题本质上可以通过更简单的主数据或流程治理解决。

停止不是失败，而是防止平台化投入在错误问题上继续扩大。

#### 3.7 方法卡

| 项目 | 内容 |
| --- | --- |
| **输入** | 候选业务问题、现状流程、数据概况、已有方案、管理目标 |
| **核心活动** | 问题澄清、替代方案比较、评分、价值假设、风险和停止条件设计 |
| **交付物** | 场景初筛表、价值假设、基线指标、继续/准备/替代/停止结论 |
| **主要角色** | 业务负责人负责价值，产品或项目负责人组织，架构与数据团队提供可行性意见 |
| **退出条件** | 有明确业务负责人、决策问题、可验证指标、初步数据路径和下一阶段授权 |

### 第 4 章 场景章程、能力问题与范围设计

#### 4.1 场景章程

场景章程用于把抽象愿景转化为可执行边界，至少包括以下内容：

1. **场景名称与业务背景**；
2. **当前问题及其业务后果**；
3. **关键决策或关键业务动作**；
4. **主要使用者和最终业务负责人**；
5. **现状流程与目标流程**；
6. **涉及的业务对象、关系、事件和规则假设**；
7. **关键数据源和已知质量问题**；
8. **能力问题清单**；
9. **价值基线、目标和约束指标**；
10. **范围、非目标和外部依赖**；
11. **风险、合规和动作可逆性**；
12. **试点验收与停止条件**。

#### 4.2 能力问题

能力问题是本体必须能够回答或支持的业务问题，也是后续建模、认证和回归测试的共同基准。

合格的能力问题应满足：

- 与具体业务决策或动作直接相关；
- 回答需要组合多个事实，而不是简单读取一个字段；
- 能够转化为可执行的查询、规则或测试用例；
- 明确时间、范围、对象和判断口径；
- 能够定义“正确答案”或至少定义可接受的评审标准。

##### 示例

不够具体：

> 查看供应商风险。

可测试的表达：

> 当一级供应商在未来 72 小时内无法供货时，识别受影响的物料、生产订单和客户订单，计算影响金额与最晚决策时间，并列出可用替代供应商及其认证状态。

##### 能力问题分解

每条能力问题建议拆为：

| 要素 | 说明 |
| --- | --- |
| **触发条件** | 什么事件或请求触发问题 |
| **核心对象** | 问题围绕哪些业务对象 |
| **关系路径** | 需要穿过哪些关系 |
| **时间语义** | 当前、历史、未来窗口或有效期 |
| **计算与规则** | 需要哪些确定性计算或业务规则 |
| **输出** | 需要返回什么事实、解释或建议 |
| **证据要求** | 输出必须引用哪些来源和时间 |
| **动作** | 是否触发审批、通知、写回或其他业务动作 |

#### 4.3 范围设计

试点范围应同时从四个维度收敛：

- **业务范围**：只覆盖一个明确决策链或流程片段；
- **模型范围**：只建设回答能力问题必需的对象和关系；
- **数据范围**：优先接入关键权威源，不以“接完所有系统”为目标；
- **行动范围**：先从只读、解释和建议开始，再逐步开放写回和自动化。

##### 非目标必须显式记录

例如：

- 本阶段不重构原 ERP 的计划算法；
- 不统一企业全部供应商主数据，只处理试点范围内的活跃供应商；
- 不实现自动下单，只提供替代供应商建议；
- 不建设全企业通用指标平台。

非目标能够避免试点在执行中不断扩张为“顺便解决所有问题”的大型平台项目。

#### 4.4 领域边界和共享对象

当对象跨越多个业务域时，需要区分：

- **领域内对象**：由单一业务域定义和治理；
- **共享核心对象**：被多个领域共同引用，例如组织、客户、供应商、产品、合同；
- **场景视图**：为特定用例组合核心对象和领域对象，但不重新复制定义。

共享对象必须指定一个语义所有者和明确的扩展机制。不同场景可以增加上下文属性或关系，但不得在未治理的情况下改变核心身份与正式定义。

#### 4.5 方法卡

| 项目 | 内容 |
| --- | --- |
| **输入** | 已通过初筛的场景、价值假设、现状流程、初步数据清单 |
| **核心活动** | 场景访谈、决策链分析、能力问题设计、范围与非目标确定、共享对象识别 |
| **交付物** | 场景章程、能力问题矩阵、范围说明、对象假设、验收与停止条件 |
| **主要角色** | 业务负责人最终确认，领域专家和本体架构师共同拆解，数据团队评估来源 |
| **退出条件** | 能力问题可测试，范围稳定，关键角色和外部依赖明确 |


### 第 5 章 数据盘点、证据管理与准备度评估

#### 5.1 目的

企业本体的模型元素和运行结果必须能够说明“从哪里来、为什么这样定义、当前是否仍然有效”。本章不是要求在建模前先完成全企业数据治理，而是识别支撑试点所必需的数据、证据和治理缺口，并决定哪些问题必须在进入认证或生产前解决。

#### 5.2 数据与知识资产清单

建议至少盘点以下资产：

1. 主数据、参考数据和编码体系；
2. 交易表、日志和历史快照；
3. 数据库模式、字段定义、主外键和约束；
4. API、消息和事件契约；
5. 代码中的实体、枚举、校验和业务规则；
6. 数据仓库、指标模型、报表和分析口径；
7. 业务制度、政策、合同、操作手册和标准；
8. 工作流、审批记录、工单和会议纪要；
9. 数据血缘、集成作业和转换逻辑；
10. 专家访谈、历史裁决和异常处理案例；
11. 外部数据、行业标准和监管要求；
12. 已有知识图谱、本体、数据模型和术语表。

资产清单不能只记录文件名或表名，还应记录责任人、访问方式、更新时间、覆盖范围、敏感等级、已知质量问题和可用状态。

#### 5.3 证据权威不是一条固定排序

数据库和代码能够证明系统“当前如何实现”，但不一定代表业务“正式应该如何定义”；制度和合同能够证明正式要求，却未必反映实际运行。因此，证据权威应根据待确认的问题类型判断。

| 待确认内容 | 优先证据 | 辅助证据 | 典型风险 |
| --- | --- | --- | --- |
| **技术结构和约束** | 数据库模式、代码、API 契约 | 技术文档、集成脚本 | 文档与真实实现不一致 |
| **正式业务定义** | 制度、标准、经批准的术语与数据标准 | 数据所有者和领域专家确认 | 制度陈旧或执行口径不同 |
| **实际业务行为** | 交易记录、日志、流程和操作记录 | 用户访谈、报表 | 历史数据可能包含违规或例外行为 |
| **法律与合规语义** | 法律法规、合同、正式政策 | 法务和合规意见 | 不同地区或时间版本不同 |
| **隐性规则与例外** | 专家访谈、历史裁决、异常案例 | 会议纪要、工单 | 个人经验可能不具代表性 |
| **身份与权威值** | 主数据、法定标识、权威外部源 | 名称、地址等模糊特征 | 同名异义、历史合并或拆分 |

当证据冲突时，不应由建模人员自行选择“看起来合理”的版本，而应形成冲突记录，明确：冲突内容、各来源、适用时间、影响范围、裁决角色和最终结论。

#### 5.4 证据坐标和溯源记录

每项候选模型元素、关键业务事实和重要评审结论都应具备可定位的证据坐标。最小字段包括：

- 来源系统、文件或知识库；
- 数据集、表、字段、接口、文档章节或代码位置；
- 来源版本或抓取时间；
- 适用时间和有效范围；
- 提取或录入方式；
- 生成、修改和确认的人员或系统；
- 与模型元素或业务事实的关联；
- 原文、摘要或不可变引用；
- 访问权限和敏感等级。

可参考“实体—活动—责任主体”的溯源结构：哪个人员或系统，在什么活动中，使用什么来源，生成或修改了哪项模型或事实。对于无法获得外部证据、但确实属于架构设计的内容，必须明确标记为**设计决策**，并记录设计理由和批准人，不能伪装成已被事实证明的结论。

#### 5.5 数据准备度评估

数据准备度应按场景而不是按全企业统一评分。建议评估以下维度：

| 维度 | 核心问题 | 可能结论 |
| --- | --- | --- |
| **可获得性** | 关键数据能否获得授权并稳定访问 | 就绪、需授权、不可获得 |
| **覆盖度** | 数据是否覆盖目标对象、时间和业务范围 | 充分、部分、关键缺口 |
| **身份一致性** | 同一对象能否跨源对齐 | 已统一、可匹配、无法稳定识别 |
| **语义清晰度** | 字段、状态和编码含义是否明确 | 清晰、存在冲突、无法解释 |
| **时间完整性** | 是否保留有效期、变更和历史快照 | 充分、部分、仅当前值 |
| **质量稳定性** | 完整、准确、唯一、一致和及时程度是否满足场景 | 达标、可治理、阻断 |
| **可追溯性** | 值和转换能否追溯到来源 | 完整、部分、黑盒 |
| **安全合规** | 数据是否允许用于当前场景、模型和部署方式 | 允许、需附加控制、禁止 |
| **运行能力** | 接口、性能和可用性是否支撑生产访问 | 就绪、需改造、不适合实时使用 |

数据问题应被分成三类处理：

- **阻断问题**：不解决就不能进入认证或生产，例如核心身份无法区分、关键数据没有合法使用依据；
- **降级问题**：可以进入有限模式，但必须降低放权级别或增加人工复核；
- **标记问题**：允许使用，但结果必须显示质量、时效或证据警告。

#### 5.6 身份解析和属性权威源

身份解析用于把多个系统中的同一业务对象对齐到统一身份。建议组合以下机制：

1. **确定性匹配**：法定标识、统一编码、序列号等强标识；
2. **规则匹配**：名称、地址、电话、组织层级等字段组合；
3. **概率匹配**：在缺少强标识时使用相似度和模型判断；
4. **人工裁决**：对高影响、低置信度或冲突记录进行确认；
5. **持续监测**：识别对象合并、拆分、名称变更和错误关联。

“一个对象有统一身份”不意味着所有属性都来自同一个系统。应按属性指定权威来源，例如供应商法定名称来自工商或供应商主数据，信用等级来自风险系统，当前交付状态来自采购执行系统。冲突解决规则应明确优先级、时间和例外条件。

#### 5.7 时间语义

企业本体至少应区分：

- **业务有效时间**：事实在业务世界中何时成立；
- **系统记录时间**：事实何时进入或被修改于系统；
- **事件发生时间**：某项业务事件实际发生的时间；
- **观察时间**：系统或人员何时获知该事实；
- **计划时间**：未来预计发生的时间窗口。

对于监管、审计、供应链影响分析和历史归因等场景，建议采用双时态或等效机制，避免用“当前数据库里的值”回答历史问题。

#### 5.8 数据契约

数据契约将模型依赖转化为可验证的承诺。每项关键数据依赖至少应明确：

- 结构、类型、取值和语义；
- 权威来源和责任人；
- 更新频率与最大允许延迟；
- 完整性、唯一性、一致性和准确性要求；
- 变更通知和兼容性规则；
- 安全等级、用途和保留策略；
- 质量异常时的阻断、降级或告警方式；
- 消费者及其业务影响。

数据字典说明“它是什么”，数据契约进一步说明“由谁以什么质量和时效提供，变化时如何处理”。

#### 5.9 接入与运行模式

根据数据特征选择批量、变更数据捕获、流式消息、API、文件、文档解析或手工登记等接入方式。选择时需要明确：

- 全量还是增量；
- 读取还是允许写回；
- 实时、准实时还是周期更新；
- 失败重试、幂等和重复处理；
- 缓存、快照和一致性策略；
- 源系统不可用时的降级；
- 删除、更正和撤回如何传播；
- Schema 变化如何通知和测试。

本体项目不应默认重新建设完整的数据集成平台，而应优先复用企业已有连接、主数据、血缘、质量和安全能力。

#### 5.10 方法卡

| 项目 | 内容 |
| --- | --- |
| **输入** | 场景章程、能力问题、初步对象假设、现有数据和知识资产 |
| **核心活动** | 资产盘点、证据分类、冲突识别、数据准备度评估、身份与时间规则设计、接入模式选择 |
| **交付物** | 资产清单、证据目录、数据准备度报告、身份规则、时间语义、数据契约草案、风险清单 |
| **主要角色** | 数据所有者对授权和质量负责，数据管家执行治理，本体架构师定义语义需求，安全与合规角色审查用途 |
| **退出条件** | 关键数据路径明确，阻断问题有解决方案，场景所需的身份、时间和证据机制可实现 |

### 第 6 章 本体发现、设计与数据映射

#### 6.1 目的

本章将业务场景、能力问题和证据转化为候选本体。目标不是一次性设计完整企业模型，而是形成能够回答当前能力问题、可以被评审、并为未来复用保留清晰边界的最小可信模型。

#### 6.2 企业级元模型

企业级本体建议至少能够表达以下元素：

| 元素 | 作用 | 示例 |
| --- | --- | --- |
| **对象类型** | 表达具有稳定身份和生命周期的业务事物 | 供应商、合同、物料、生产订单 |
| **属性** | 描述对象自身特征 | 合同金额、物料编码、风险等级 |
| **关系类型** | 表达两个或多个对象之间的业务联系 | 供应商供应物料、订单占用产能 |
| **事件类型** | 表达在某个时间发生并改变业务状态的事实 | 停产、签约、收货、付款 |
| **状态与状态转换** | 表达对象所处阶段及允许的变化 | 合同草拟→审批→生效→终止 |
| **业务规则** | 表达确定性约束、分类和判断逻辑 | 超过阈值需要二级审批 |
| **指标与度量** | 表达计算口径、单位和时间窗口 | 受影响订单金额、缺料天数 |
| **动作类型** | 表达可被人员、应用或 Agent 调用的业务能力 | 发起审批、冻结付款、创建替代采购申请 |
| **策略与权限** | 约束谁在什么条件下可以读取或执行 | 仅采购负责人可批准替代供应商 |
| **证据与溯源** | 说明模型和事实如何产生 | 来源表、文档章节、评审记录 |

不同技术平台可以用不同方式实现这些元素，但方法论层面必须明确其语义和治理责任。

#### 6.3 核心建模决策

##### 对象还是属性

当一个概念具有独立身份、生命周期、关系、责任或需要被多个场景引用时，应优先建成对象；只描述另一个对象、没有独立生命周期的值通常作为属性。

例如，“供应商注册地址”可以是属性；如果企业需要管理多个地址、地址有效期、地址类型和地址风险，则“地址”可以成为独立对象。

##### 关系还是中间对象

简单、稳定的二元联系可以建成关系。当联系本身具有金额、时间、状态、责任或其他属性时，应建成关联对象。

例如，“供应商供应物料”如果仅表示存在关系，可以直接建边；如果需要表达价格、起止日期、认证状态、采购份额和交付条款，则更适合建成“供应关系”对象。

##### 类型还是实例

“战略供应商”可能是供应商的分类值，也可能是具有单独规则和生命周期的角色。建模前必须明确它是类型、状态、角色还是具体对象，避免把分类标签和业务实体混在一起。

##### 事件还是状态

事件表示“发生了什么”，状态表示“当前处于什么阶段”。例如“合同已签署”是状态，“合同签署事件”记录签署人、时间、版本和证据。高审计场景通常需要同时表达事件和状态。

##### 规则还是模型结构

稳定、普遍且属于语义约束的内容可以进入模型约束；经常变化、依赖政策参数或需要独立发布的逻辑，通常应进入规则服务或策略层。避免把所有业务规则硬编码为本体结构。

#### 6.4 身份、粒度和生命周期

每个核心对象必须明确：

- 对象的最小业务粒度；
- 唯一身份规则和替代标识；
- 创建、合并、拆分、失效和删除规则；
- 历史身份和别名如何保留；
- 对象由哪个业务域拥有；
- 哪些属性可以被其他领域扩展；
- 是否允许一个源记录映射多个对象，或多个源记录映射同一对象。

“一个对象类型对应一张表”不是强制规则。一个对象可以由多张表、API 和文档共同形成；一张表也可能包含多个业务对象。映射必须以业务语义和粒度为准，而不是机械照搬物理表结构。

#### 6.5 命名空间与跨域复用

建议采用“共享核心 + 领域扩展 + 场景视图”的结构：

```text
企业共享核心
组织｜人员｜客户｜供应商｜产品｜合同｜地点｜时间
        ↓
领域本体
采购｜制造｜财务｜销售｜风险｜服务
        ↓
场景视图
供应中断影响｜关联交易审查｜合同付款真实性
```

共享核心只保留跨域稳定语义，领域扩展负责专业属性、关系和规则，场景视图负责组合使用，不复制所有定义。跨域冲突由明确的治理机制仲裁，而不是由最后修改模型的人决定。

#### 6.6 证据驱动的发现流程

候选建设可以划分为六个步骤：

| 步骤 | 核心活动 | 主要产物 | 质量要求 |
| --- | --- | --- | --- |
| **D0 准备** | 确认场景、能力问题、资产、权限和输出结构 | 任务说明、输入清单 | 边界和数据使用条件明确 |
| **D1 提取** | 从数据、代码、文档和访谈中抽取术语、对象、关系、规则与动作候选 | 候选清单、证据片段 | 候选与来源保持关联 |
| **D2 归一** | 处理同义异名、同名异义、重复对象和编码差异 | 术语映射、身份候选、冲突清单 | 不静默合并冲突语义 |
| **D3 建模** | 确定对象粒度、关系、事件、状态、规则、指标和动作 | 候选模型 | 能够覆盖能力问题的核心路径 |
| **D4 映射与验证** | 建立源数据映射，运行结构校验和样例查询 | 映射草案、验证结果 | 关键路径能在样例数据上运行 |
| **D5 打包** | 汇总模型、证据、决策、问题、质量和版本 | 候选本体包 | 可被独立评审和复现 |

#### 6.7 人工与 AI 的分工

**默认建议：AI 生成候选，人类承担语义判断和责任。**

AI 适合：

- 术语、对象、关系、规则和动作候选抽取；
- 相似概念聚类和映射建议；
- 证据片段关联；
- 命名、描述和文档草稿生成；
- 结构校验、测试生成和变更影响辅助分析。

人类必须负责：

- 确认业务含义、身份和粒度；
- 裁决冲突、例外和政策含义；
- 决定共享与领域边界；
- 批准高风险规则、动作和权限；
- 对最终发布和业务后果承担责任。

AI 输出必须结构化，并携带来源、模型版本、提示或任务版本和置信信息。置信度不能只来自模型自评，应综合证据质量、多源一致性、明确约束、历史评审表现和冲突情况。

#### 6.8 数据映射

每项关键映射应说明：

- 目标对象、属性、关系或事件；
- 来源系统、表、字段、接口或文档；
- 转换、清洗和单位换算逻辑；
- 身份匹配和去重规则；
- 时间字段和有效期；
- 空值、冲突和异常处理；
- 数据责任人和质量要求；
- 写回方向和限制；
- 变更和版本兼容性。

映射不是简单字段对字段连接。它是源数据结构与正式业务语义之间的可测试契约。

#### 6.9 候选本体包

候选本体包至少包括：

1. 模型图和机器可读模型；
2. 元素清单与正式描述草案；
3. 能力问题覆盖矩阵；
4. 数据映射草案；
5. 证据覆盖和设计决策记录；
6. 身份、时间和状态规则；
7. 自动结构校验结果；
8. 冲突、假设和待确认问题；
9. 低置信度和高风险元素清单；
10. 版本、作者、生成工具和输入范围。

##### 典型反模式

- 直接把数据库表结构重新画成图；
- 只有对象名，没有正式定义、身份和生命周期；
- 关系没有方向、角色、基数、时间或适用范围；
- 把状态、事件、类型和角色混为一谈；
- 每个项目重新复制客户、供应商、合同等核心对象；
- 动作没有权限、前置条件、后果和回滚定义；
- AI 生成的候选没有证据和任务版本；
- 为追求“全”而加入大量当前场景无法验证的概念。

#### 6.10 方法卡

| 项目 | 内容 |
| --- | --- |
| **输入** | 场景章程、能力问题、证据目录、数据准备度报告、已有模型和标准 |
| **核心活动** | 候选提取、术语归一、元模型设计、身份与时间建模、跨域复用、数据映射和结构验证 |
| **交付物** | 候选本体包、映射草案、覆盖矩阵、问题与风险清单 |
| **主要角色** | 本体架构师负责结构，领域专家确认业务语义，数据工程师负责映射，AI 可辅助生成候选 |
| **退出条件** | 核心能力问题有模型路径，关键元素可追溯，结构校验通过，未决问题可进入正式评审 |

### 第 7 章 语义认证、质量验证与发布准备

#### 7.1 目的

认证的目标不是证明模型“看起来合理”，而是建立组织可以依赖的正式语义契约，并确认该模型在业务、数据、结构、运行和消费者层面达到当前场景所需的质量。

#### 7.2 语义契约

每个核心对象、关系、事件、指标和动作都应具有可审查的语义契约。对象语义契约建议包含：

1. 业务名称、技术名称和命名空间；
2. 正式定义及业务目的；
3. 适用范围和明确不适用范围；
4. 对象粒度、身份和生命周期；
5. 属性定义、单位、编码和空值语义；
6. 关系含义、方向、角色、基数和时间；
7. 事件、状态及允许的状态转换；
8. 相关规则、指标和动作；
9. 权威数据来源和映射；
10. 质量、时效和证据要求；
11. 权限、敏感性和合规约束；
12. 责任人、维护者和消费者；
13. 正例、反例、例外和已知限制；
14. 版本、兼容性和变更历史。

语义契约必须能够被业务人员理解，也能够被技术系统验证。只包含技术 Schema、没有业务边界的文件不能替代语义契约。

#### 7.3 评审机制

评审应至少覆盖四类视角：

- **业务视角**：定义是否符合真实业务和决策需求；
- **数据视角**：数据是否能够支撑该语义，权威源和质量是否明确；
- **架构视角**：结构是否一致、可复用、可演进并符合元模型；
- **消费者视角**：应用、分析或 Agent 是否能够按预期使用，兼容性是否可接受。

对每项候选元素，评审可以给出六种结论：

1. 接受；
2. 接受但修改；
3. 与已有元素合并；
4. 拆分为多个元素；
5. 否决；
6. 搁置并等待补证。

每项结论必须记录理由、依据、影响和责任人。提交者不得独自批准自己的变更；高风险语义、动作或权限需要额外的独立评审。

#### 7.4 分层质量模型

不建议用一个固定权重的总分替代所有质量判断。应至少分成四层：

##### 模型质量

- 定义是否清晰且无循环解释；
- 对象粒度、身份、关系和生命周期是否一致；
- 能力问题是否被覆盖；
- 是否存在重复概念、孤立对象或未经治理的跨域冲突；
- 命名、约束和复用是否符合规范。

##### 数据质量

- 关键字段是否完整、准确、唯一、一致和及时；
- 身份解析是否可靠；
- 时间和历史是否充分；
- 映射和转换能否追溯；
- 质量问题是否具有责任人和处理策略。

##### 运行质量

- 查询和动作的性能、可用性和稳定性；
- 数据更新延迟和失败率；
- 权限执行、审计和告警是否有效；
- 回滚、降级和恢复是否经过验证。

##### 业务质量

- 输出是否支持目标决策；
- 误判、漏判和人工复核是否在可接受范围；
- 用户是否采用；
- 业务时长、风险、成本、收入或交付指标是否改善。

不同场景应设置不同门槛。例如监管穿透更重视证据、时间和完整性，实时供应链更重视新鲜度、性能和影响计算准确性。

#### 7.5 自动验证

建议将以下检查自动化：

- 语法和 Schema 校验；
- 名称、命名空间和唯一性检查；
- 关系方向、角色、基数和域值范围；
- 状态转换和动作前置条件；
- 证据、责任人和版本字段完整性；
- 数据映射是否引用存在的来源和字段；
- 能力问题对应的查询和结果结构；
- 下游消费者兼容性；
- 安全策略和敏感字段使用；
- 与上一版本的语义差异和影响范围。

自动检查只能证明规则已被满足，不能替代业务语义评审。

#### 7.6 能力问题作为验收测试

每条能力问题应转化为一个或多个测试：

- 测试输入与时间窗口；
- 预期对象和关系路径；
- 预期计算、规则和输出结构；
- 应引用的证据和来源；
- 正常、边界和异常样例；
- 准确性、完整性、性能和解释要求；
- 版本变更后的回归结果。

对于无法预先给出唯一答案的判断型问题，应建立专家标注集、可接受区间或评审准则，而不是让模型自行判断自己是否正确。

#### 7.7 认证发布条件

认证版本至少应满足：

- 场景、范围和能力问题仍然有效；
- 核心语义契约完成并获批准；
- 关键数据映射、身份和时间规则明确；
- 阻断级结构和数据问题已关闭；
- 自动测试和能力问题测试达到场景门槛；
- 未解决风险、限制和降级方式已记录；
- 版本、责任人、消费者和兼容性影响明确；
- 安全、隐私和动作权限已完成必要审查；
- 生产验证计划和回滚原则已确定。

#### 7.8 认证本体包

认证本体包应包括：

1. 已批准的机器可读模型和可阅读模型说明；
2. 语义契约；
3. 数据映射和数据契约；
4. 能力问题与测试结果；
5. 模型、数据和安全质量报告；
6. 评审记录与未决风险；
7. 版本、兼容性和迁移说明；
8. 消费者清单和使用约束；
9. 生产验证与发布计划；
10. 责任和维护安排。

#### 7.9 方法卡

| 项目 | 内容 |
| --- | --- |
| **输入** | 候选本体包、场景章程、证据与数据报告、消费者需求 |
| **核心活动** | 语义契约编制、跨角色评审、自动验证、能力问题测试、风险与兼容性评估 |
| **交付物** | 认证本体包、质量报告、评审记录、生产验证计划 |
| **主要角色** | 业务负责人批准业务适用性，本体所有者批准语义版本，数据所有者确认数据承诺，架构和安全角色完成专业审查 |
| **退出条件** | 发布条件全部满足，未决风险有明确接受人和控制措施，可进入非破坏性的生产验证 |


## 第三部分：从可信模型到生产运营

### 第 8 章 集成、消费与渐进放权

#### 8.1 目的

认证本体只有被业务人员、应用或 AI Agent 持续使用，才能产生价值。进入生产的关键不是一次性开放全部能力，而是在可观察、可复核、可回退的条件下逐步增加影响范围和行动权限。

#### 8.2 四类消费方式

| 消费方式 | 典型能力 | 主要使用者 | 核心控制 |
| --- | --- | --- | --- |
| **查询与浏览** | 对象检索、关系穿透、历史追溯、证据查看 | 业务人员、审计、分析人员 | 对象和属性级权限、来源与时间提示 |
| **分析与决策服务** | 影响分析、指标计算、规则判断、场景模拟 | 运营和管理人员、业务应用 | 口径版本、输入质量、解释和结果校验 |
| **应用编程接口** | 对象 API、事件订阅、语义查询、SDK | 应用与数据产品团队 | 契约、限流、兼容性、消费者登记 |
| **动作与 Agent** | 发起审批、通知、写回、调用工具、受限自动执行 | 业务应用、自动化系统、AI Agent | 身份、权限、前置条件、审批、审计、回滚和停机 |

消费者不应直接绕过本体语义和权限规则访问底层数据并自行重新解释。对于确有性能或技术原因需要直连的场景，也应通过数据契约和版本约束保持一致。

#### 8.3 生产前验证

认证完成后，先在不影响真实业务的条件下验证：

1. **历史回放**：用历史数据重现已知事件，比较本体输出与实际结果或专家判断；
2. **边界测试**：验证空值、冲突、延迟、重复、身份错误和异常状态；
3. **影子运行**：与现有人工或系统流程并行运行，只记录结果，不改变业务；
4. **用户验收**：确认输出是否可理解、可解释、可操作，是否适应实际工作节奏；
5. **运营演练**：模拟数据中断、权限错误、版本回滚和动作失败。

生产前验证不仅评估模型准确性，还要评估数据时效、系统稳定性、人员采用和异常处理成本。

#### 8.4 五级渐进放权

| 级别 | 运行方式 | 业务影响 | 升级证据 |
| --- | --- | --- | --- |
| **L1 历史回放** | 在历史数据上验证 | 无实时业务影响 | 覆盖率、正确性、解释和边界测试达到门槛 |
| **L2 影子运行** | 与当前流程并行，只记录不生效 | 无直接业务影响 | 连续运行稳定，差异原因可解释 |
| **L3 辅助决策** | 系统提供结论和建议，由人决定 | 人承担最终判断 | 采纳率、误判率、人工负担和业务效果达标 |
| **L4 可逆写回** | 系统可执行有限写回，但需审批或可撤销 | 有限且可恢复 | 权限、幂等、审批、补偿和回滚经过验证 |
| **L5 受限自动化** | 在明确边界内自动执行 | 直接影响业务 | 风险边界、监控、停机和事后审计成熟 |

放权级别应针对具体动作，而不是针对整个本体统一设置。同一场景中，“查询影响订单”可以达到 L5 自动运行，“更换供应商”可能长期停留在 L3 或 L4。

#### 8.5 动作契约

任何可执行动作必须定义：

- 动作名称、目的和业务后果；
- 调用者、授权角色和适用环境；
- 输入、输出和对象身份；
- 前置条件、禁止条件和业务规则；
- 是否需要人工审批及审批层级；
- 幂等、超时、重试和并发规则；
- 对源系统的写回方式；
- 成功、部分成功和失败的定义；
- 补偿、撤销和回滚方式；
- 审计字段、证据和保留期限；
- 风险等级和紧急停用开关。

动作契约必须与语义契约和数据契约保持一致。模型中存在一个动作名称，并不意味着该动作已经具备安全执行条件。

#### 8.6 确定性逻辑与 AI 的分工

**默认原则：能够明确表达为确定性规则的逻辑，应优先采用确定性实现；AI 用于处理需要归纳、分类、匹配、解释或不完全信息判断的部分。**

例如：

- “关联交易金额超过批准阈值必须升级审批”适合确定性规则；
- “合同付款材料是否存在明显业务异常”可以由 AI 进行初步判断，但需要引用证据、输出不确定性并保留人工复核；
- “根据多个中断信号形成可能受影响供应商清单”可以使用模型辅助；
- “自动冻结付款”属于高影响动作，必须由明确规则、授权和审批控制，不能只依据生成式模型文本决定。

AI 结果应作为带来源、模型版本和置信信息的判断输入，而不是未经验证的正式事实。

#### 8.7 生产质量闸门

生产运行至少应持续监控：

- **业务正确性**：输出是否仍符合业务定义和决策要求；
- **数据状态**：关键数据是否新鲜、完整且身份可解析；
- **模型状态**：当前运行版本、依赖和兼容性是否正常；
- **系统状态**：延迟、吞吐、错误率和可用性；
- **动作状态**：成功、失败、重试、补偿和人工接管；
- **安全状态**：异常访问、越权、敏感数据暴露和策略命中；
- **采用状态**：使用率、建议采纳率、人工绕过和用户反馈；
- **价值状态**：目标业务指标和约束指标是否持续达标。

闸门异常时应有明确的处理级别：告警、结果标记、降级、暂停动作、回退版本或停止服务。

#### 8.8 可观测性和解释

每次重要查询、判断和动作应能够回答：

- 使用了哪个本体版本；
- 使用了哪些数据和证据；
- 数据在什么时间有效、何时被系统观察；
- 应用了哪些规则、模型或提示版本；
- 哪个用户、应用或 Agent 发起；
- 为什么得到该结果；
- 是否经过人工修改或批准；
- 最终产生了什么业务后果；
- 发生异常时如何恢复。

对于高风险判断，解释不能只是一段模型生成的自然语言，而应包含可验证的对象路径、规则命中和证据引用。

#### 8.9 反馈回路

生产中的差异和人工判断应回流到：

- 能力问题和测试集；
- 术语、身份和映射规则；
- 语义契约和业务规则；
- AI 提示、评估集和模型选择；
- 数据治理任务；
- 用户界面和业务流程；
- 产品化模板和下一场景设计。

反馈不能只保留“接受或拒绝”，还应记录理由、证据和最终结果，才能形成组织学习。

#### 8.10 方法卡

| 项目 | 内容 |
| --- | --- |
| **输入** | 认证本体包、生产验证计划、应用与动作需求、权限和运行约束 |
| **核心活动** | 接口与工作台集成、历史回放、影子运行、用户验收、动作契约、监控和渐进放权 |
| **交付物** | 生产验证报告、部署配置、动作契约、权限策略、监控面板、运营与回滚手册 |
| **主要角色** | 业务负责人批准业务使用和放权，产品与工程团队实施，安全和平台运营负责控制与监测 |
| **退出条件** | 当前放权级别的质量和风险门槛持续满足，异常处理和人工接管机制可用 |

### 第 9 章 生命周期、变更治理与 CI/CD

#### 9.1 目的

本体一旦被多个应用和业务流程消费，任何语义变化都可能影响查询、规则、指标、权限和动作。本章建立类似软件工程但面向语义资产的变更和交付机制。

#### 9.2 本体即代码

“本体即代码”不是要求所有业务人员直接编辑代码，而是要求本体具备以下工程属性：

- 每次变更有提交人、理由、时间和关联场景；
- 可以在独立工作区或分支中试验；
- 变更能够产生机器可读和人可读的语义差异；
- 自动测试和评审可以在合并前执行；
- 发布版本不可被静默覆盖；
- 任意生产结果能够关联到当时的模型版本；
- 失败时可以回退或迁移。

图形编辑器、表格、表单和代码视图都可以作为编辑入口，但底层应进入同一版本和审计体系。

#### 9.3 变更类型

变更至少分为：

- **描述性变更**：补充说明、示例或证据，不改变正式语义；
- **兼容性扩展**：新增可选属性、对象或关系，不破坏现有消费者；
- **行为变更**：规则、指标、状态转换或动作结果发生变化；
- **破坏性变更**：删除、重命名、改变身份、粒度、关系方向或语义；
- **治理变更**：责任、权限、敏感等级或生命周期发生变化；
- **数据映射变更**：来源、转换、权威源或时间规则变化。

风险等级应根据实际影响判断，不能只依据修改文件的数量。

#### 9.4 语义差异和影响分析

一次变更提案应自动或人工回答：

- 新增、删除或修改了哪些模型元素；
- 正式定义、身份、粒度、时间或基数是否变化；
- 哪些数据映射和契约受影响；
- 哪些能力问题、查询、规则、指标和动作需要重测；
- 哪些应用、报表、Agent 和业务流程是消费者；
- 是否需要数据迁移、双版本运行或消费者改造；
- 是否引入安全、隐私或监管影响；
- 是否改变已有历史事实的解释。

语义差异必须提供业务可读描述，不能只展示底层 RDF、JSON 或代码行变化。

#### 9.5 版本策略

可以采用“主版本.次版本.修订版本”等语义化版本，但审批不能机械地只与版本号绑定。建议：

- 修正文档、证据或不影响语义的错误，通常作为修订版本；
- 向后兼容的新增能力，通常作为次版本；
- 改变身份、粒度、正式含义或删除已有能力，通常作为主版本；
- 高风险动作、隐私策略或监管口径变化，即使技术上兼容，也需要加强审批。

版本说明必须包含业务影响、消费者影响、迁移方式、已知限制和回退条件。

#### 9.6 环境与发布管线

**默认建议：** 至少区分开发、验证和生产环境，禁止未经验证直接修改生产资产。

典型发布管线：

```text
变更提案
  → 结构与规范校验
  → 语义差异与影响分析
  → 数据映射和契约测试
  → 能力问题与回归测试
  → 安全、隐私和动作检查
  → 消费者兼容性验证
  → 独立评审与批准
  → 验证环境部署
  → 生产发布或灰度
  → 发布后观察与确认
```

不同风险的变更可以使用不同强度的管线，但任何生产变更都不能跳过版本记录和影响评估。

#### 9.7 兼容、迁移和废弃

破坏性变更应优先采用以下方式降低影响：

- 新旧版本并行一段时间；
- 提供别名、转换或兼容层；
- 发布迁移脚本和消费者改造指南；
- 明确废弃日期和责任人；
- 监控仍在使用旧版本的消费者；
- 在归档前保留历史解释能力。

删除模型元素不等于删除历史业务事实。历史数据应能够按照当时版本被正确解释和审计。

#### 9.8 漂移检测

需要持续检测四类漂移：

1. **源结构漂移**：表、字段、接口或消息发生变化；
2. **数据分布漂移**：取值、缺失、异常和身份匹配特征发生变化；
3. **业务语义漂移**：制度、流程、状态和实际操作口径发生变化；
4. **消费行为漂移**：下游开始以非预期方式解释或使用模型。

漂移检测结果应说明影响对象、消费者、业务风险和建议处理方式，而不是只发出技术告警。

#### 9.9 回滚与恢复

回滚方案应区分：

- 模型版本回退；
- 数据映射回退；
- 规则或动作版本回退；
- 已写回业务系统的数据补偿；
- 消费者缓存和派生结果清理；
- 生产期间生成的新事实如何重新解释。

对于不可逆动作，单纯回滚本体版本不能恢复业务后果，必须在动作设计阶段定义补偿流程和责任人。

#### 9.10 方法卡

| 项目 | 内容 |
| --- | --- |
| **输入** | 已认证或生产本体、变更需求、消费者清单、数据和安全依赖 |
| **核心活动** | 变更分类、语义差异、影响分析、测试、审批、部署、观察、迁移和废弃 |
| **交付物** | 变更提案、差异报告、测试结果、版本说明、迁移与回滚方案 |
| **主要角色** | 本体所有者对版本负责，架构师和数据团队实施，消费者验证兼容性，业务和安全角色按风险批准 |
| **退出条件** | 变更效果与影响可解释，测试和审批完成，发布后状态稳定，回退路径有效 |

### 第 10 章 安全、合规与运行可靠性

#### 10.1 目的

企业本体将原本分散的数据、关系和动作集中到统一语义层，既提升能力，也可能放大敏感数据关联、越权查询和自动行动风险。安全与合规必须从场景设计开始，而不是上线前补充审批。

#### 10.2 数据分类与用途约束

每个对象和属性应标记：

- 数据分类和敏感等级；
- 法律、合同或企业政策依据；
- 允许的业务用途和禁止用途；
- 可访问的角色、组织、地区和环境；
- 是否允许进入外部模型或第三方服务；
- 是否需要脱敏、聚合、匿名化或最小化；
- 保留期限、删除和审计要求。

本体能够揭示原本不容易发现的关系，因此需要评估“组合后敏感性”。多个普通字段组合后可能推断出敏感身份、交易或风险信息。

#### 10.3 权限模型

权限应覆盖多个层次：

1. 租户和组织边界；
2. 命名空间、领域和场景；
3. 对象类型和具体对象；
4. 属性和关系；
5. 查询、导出、推理和批量访问；
6. 规则、动作和写回；
7. 环境、时间、地点和设备等上下文条件。

可以组合角色访问控制和属性访问控制。高敏感关系、批量穿透查询和高影响动作通常需要更细粒度授权、二次确认或审批。

#### 10.4 最小权限与职责分离

至少应落实：

- 提交变更的人不能独自批准；
- 模型结构、业务语义、数据授权和生产发布不由同一角色完全控制；
- Agent 使用独立服务身份，不继承操作者全部权限；
- 读取权限不自动包含导出、推理或写回权限；
- 高风险动作使用短时授权、审批或多方确认；
- 紧急权限必须有时限、理由和事后审计。

#### 10.5 AI 特有风险

使用大模型辅助建设或消费本体时，应额外治理：

- 提示注入和工具劫持；
- 将敏感数据发送到不允许的模型或区域；
- 模型生成无证据的对象、关系或判断；
- 上下文截断导致遗漏重要约束；
- 模型或提示版本变化引发结果漂移；
- Agent 越权调用工具或串联多个低风险动作形成高风险后果；
- 第三方模型、插件和数据处理方的供应链风险；
- 成本、延迟和不可用导致业务降级。

控制措施包括输入隔离、内容和工具白名单、结构化输出、证据校验、最小权限、模型评估、动作审批、沙箱执行和完整日志。

#### 10.6 审计记录

审计记录应覆盖：

- 模型和语义契约的创建、修改、评审和发布；
- 数据访问、查询、导出和批量操作；
- AI 使用的数据、任务、模型和输出版本；
- 动作调用、审批、写回、失败和补偿；
- 权限授予、拒绝、变更和紧急访问；
- 异常告警、人工接管、停机和恢复；
- 业务结果被人工修改或否决的原因。

审计日志本身需要不可篡改、访问受控，并按照业务和监管要求保留。

#### 10.7 可靠性设计

生产本体需要明确服务目标，例如：

- 查询和动作的可用性；
- 端到端延迟；
- 数据最大允许陈旧时间；
- 身份解析和映射失败率；
- 动作成功、重试和补偿成功率；
- 告警响应和恢复时间；
- 关键消费者的降级方式。

这些参数应由场景风险决定。用于辅助浏览的服务和用于阻断付款的服务，不应采用相同的可靠性和审批门槛。

#### 10.8 降级与安全停机

至少准备以下降级模式：

- 暂停自动动作，保留只读查询；
- 停止使用过期或质量不达标的数据源；
- 回退到上一模型、规则或映射版本；
- 将判断转为人工复核；
- 仅返回事实和证据，不返回建议；
- 切换到现有业务系统的原流程；
- 完全停止服务并通知消费者。

停机开关必须有明确授权、触发条件、通知机制和恢复步骤，并定期演练。

#### 10.9 事故响应

事故处理流程建议包括：

1. 识别影响范围和风险等级；
2. 暂停相关动作或切换降级模式；
3. 固化日志、证据和版本；
4. 通知业务、数据、安全和消费者负责人；
5. 修复模型、数据、权限或系统问题；
6. 验证并逐步恢复；
7. 评估是否需要纠正已产生的业务结果；
8. 将根因和处置结果回流到规则、测试和运营手册。

#### 10.10 方法卡

| 项目 | 内容 |
| --- | --- |
| **输入** | 场景、数据分类、模型和动作设计、部署方式、消费者与监管要求 |
| **核心活动** | 风险建模、用途和权限设计、AI 安全评估、可靠性目标、降级停机和事故演练 |
| **交付物** | 安全与合规评估、权限策略、审计方案、可靠性目标、停机与事故响应手册 |
| **主要角色** | 业务和数据所有者确认用途，安全、隐私、法务和平台团队负责专业控制，运营团队执行监测和响应 |
| **退出条件** | 关键风险有控制和责任人，动作可被暂停或接管，审计与恢复能力经过验证 |


## 第四部分：组织、价值与规模化

### 第 11 章 组织架构与运营模式

#### 11.1 目的

企业本体既涉及业务定义，也涉及数据、架构、软件工程、安全和生产运营。没有清晰的责任设计，本体容易变成“人人都能提意见、无人对结果负责”的共享资产。本章定义组织层级、角色、RACI 和日常运营机制。

#### 11.2 推荐的联邦式组织结构

**默认建议：采用“中央能力中心 + 领域团队 + 业务场景团队”的联邦模式。**

##### 企业级治理层

由企业架构、数据、业务、风险和技术管理者组成，主要负责：

- 确定企业级原则、优先级和投资方向；
- 批准共享核心对象和跨域标准；
- 仲裁跨领域语义、身份和数据权威冲突；
- 制定安全、隐私、外部模型和高风险动作政策；
- 审查重大版本、平台风险和规模化投资。

##### 本体与语义能力中心

作为中央卓越中心，主要负责：

- 维护元模型、建模规范和共享核心；
- 提供本体工程平台、版本、测试和发布能力；
- 培养本体架构师和现场建模工程师；
- 审查跨域复用和破坏性变更；
- 沉淀模板、评估集、案例和最佳实践；
- 支持领域团队解决复杂建模问题。

##### 领域本体团队

嵌入采购、制造、财务、销售、风险等领域，主要负责：

- 维护领域语义和数据映射；
- 与领域专家共同评审对象、关系、规则和指标；
- 处理领域内数据质量和语义漂移；
- 支持多个场景复用领域资产。

##### 场景交付团队

围绕具体业务场景组建，通常包括业务负责人、产品或项目负责人、本体架构师、数据工程师、领域专家、应用工程师和运营人员，负责从价值假设到生产验收的完整闭环。

#### 11.3 核心角色与责任

| 角色 | 核心责任 | 不应被替代的职责 |
| --- | --- | --- |
| **业务负责人** | 对场景优先级、流程变化、采用和业务价值负责 | 最终业务结果和放权决定 |
| **产品/项目负责人** | 组织范围、计划、依赖、交付和用户采用 | 将业务目标转化为可交付闭环 |
| **本体所有者** | 对特定本体域的正式语义、版本和生命周期负责 | 批准语义版本和跨场景一致性 |
| **数据所有者** | 对数据授权、质量目标、权威来源和数据契约负责 | 决定数据用途和质量责任 |
| **数据管家** | 执行日常数据治理、字典维护、问题修复和质量跟踪 | 保持数据承诺在运营中有效 |
| **本体架构师** | 设计对象、关系、事件、规则、动作和复用边界 | 对模型结构和工程质量负责 |
| **领域专家** | 确认业务定义、例外、规则和真实操作 | 业务语义判断和专业例外确认 |
| **平台与数据工程团队** | 实现接入、映射、服务、版本、测试、部署和监控 | 生产工程与可靠性 |
| **安全、隐私与合规角色** | 审查用途、权限、外部模型、敏感数据和高风险动作 | 对专业风险提出约束或否决意见 |
| **消费者负责人** | 确认接口、兼容性、使用约束和消费结果 | 对下游使用方式和改造负责 |
| **运营与支持团队** | 监控运行、处理告警、事故、回滚和用户问题 | 保持生产服务可用和可恢复 |

#### 11.4 活动级 RACI 示例

RACI 必须针对具体活动定义，而不是给某个角色永久贴上一个字母。每项活动原则上只能有一个最终问责者 A。

缩写：业务负责人（BO）、产品负责人（PO）、本体所有者（OO）、数据所有者（DO）、本体架构师（OA）、领域专家（DE）、平台运营（PE）、安全合规（SC）、消费者负责人（CO）。

| 活动 | BO | PO | OO | DO | OA | DE | PE | SC | CO |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 场景选择与价值假设 | **A** | R | C | C | C | C | I | C | C |
| 场景范围与能力问题 | **A** | R | C | C | R | R | I | C | C |
| 数据授权与质量承诺 | C | C | C | **A** | C | C | R | C | I |
| 候选本体建设 | C | C | C | C | **A** | R | R | I | C |
| 正式语义认证 | C | C | **A** | C | R | R | C | C | C |
| 安全与高风险动作批准 | C | I | C | C | C | C | R | **A** | I |
| 生产部署与运行 | I | C | C | C | R | I | **A** | C | C |
| 业务采用与流程变更 | **A** | R | C | I | C | R | C | C | R |
| 版本兼容与消费者迁移 | I | C | **A** | C | R | C | R | C | R |
| 生产事故响应 | I | C | C | C | R | I | **A** | R | C |
| 价值复盘与扩展决策 | **A** | R | C | C | C | C | C | I | C |

该表是示例。企业应根据自身组织将角色映射到具体岗位，但不能省略最终问责人。

#### 11.5 集中式、嵌入式与混合模式

| 模式 | 优点 | 局限 | 适用阶段 |
| --- | --- | --- | --- |
| **集中式** | 标准统一、平台复用、人才集中、跨域仲裁方便 | 离业务较远，响应和语义理解可能不足 | 共享核心、平台建设、规模治理 |
| **嵌入式** | 贴近业务、反馈快、易建立信任 | 容易形成领域孤岛和重复模型 | 早期试点、复杂业务探索 |
| **混合式** | 业务深度与企业标准兼顾 | 需要明确双重汇报和决策边界 | 大多数进入规模化的企业 |

实践中通常采用：试点阶段以嵌入式场景团队为主，同时接受中央能力中心的架构约束；规模化后由领域团队长期拥有模型，中央团队维护共享核心和平台。

#### 11.6 治理会议与运营节奏

建议建立不同层级的固定节奏：

- **每周场景工作会**：处理能力问题、数据缺口、模型问题和交付阻塞；
- **双周或月度语义评审会**：审查候选、冲突、共享对象和变更提案；
- **月度生产运营会**：检查质量、事件、采用、版本、消费者和技术债务；
- **季度价值与路线图评审**：审查业务结果、复用价值、投资和停止/扩展决策；
- **重大变更专项评审**：处理破坏性版本、高风险动作、隐私和监管变化。

会议必须以交付物和决策为中心，避免变成没有明确结论的概念讨论。

#### 11.7 人才与能力模型

企业本体的关键能力不是单一“图谱工程师”，而是跨越以下领域：

- 业务流程和领域知识；
- 数据建模、主数据和数据质量；
- 本体、知识表示和语义建模；
- API、事件、规则和业务动作；
- 软件工程、测试、版本和 DevOps；
- 安全、隐私和风险治理；
- AI 工程、评估和 Agent 运行时；
- 产品管理、用户采用和价值衡量。

现场建模工程师需要能够在业务语言、数据结构和可执行系统之间翻译。该角色不能只懂技术，也不能只做会议记录。

#### 11.8 资金与资源机制

建议将投入分为两类：

- **平台与共享能力投入**：由企业级预算支持元模型、版本、测试、权限、核心对象和通用工具；
- **场景价值投入**：由业务场景承担数据治理、模型扩展、应用集成、流程改造和采用成本。

这样既避免每个场景重复建设平台，也防止中央团队建设大量没有消费者的“通用能力”。

#### 11.9 组织运营指标

可持续运营应关注：

- 认证和生产本体数量及复用率；
- 变更交付周期和审批积压；
- 共享对象冲突和重复定义数量；
- 数据契约违约和修复时间；
- 消费者数量、调用和采用率；
- 生产事故、越权和回滚情况；
- 专家评审结论回流率；
- 场景价值实现率和平台复用节省。

这些指标用于识别治理效率和资产复利，不应仅以“建了多少对象和关系”评价团队。

#### 11.10 方法卡

| 项目 | 内容 |
| --- | --- |
| **输入** | 企业组织结构、数据治理机制、架构职责、试点路线图和平台边界 |
| **核心活动** | 角色设计、RACI、中央与领域分工、会议机制、人才和预算设计 |
| **交付物** | 组织章程、角色说明、活动级 RACI、治理节奏、能力与资源计划 |
| **主要角色** | 企业管理层批准治理结构，业务、数据、架构、安全和技术负责人共同落地 |
| **退出条件** | 每项关键活动有唯一问责者，场景和平台均有长期运营责任与资源 |

### 第 12 章 业务价值实现与规模化

#### 12.1 目的

本体上线不等于业务价值已经实现。价值来自模型改变了某项决策、流程或行动，并被用户持续采用。本章建立从基线、流程改造、采用、归因到规模化的完整机制。

#### 12.2 价值实现链

```text
可信对象与关系
    ↓
更完整、更及时、更一致的业务信息
    ↓
新的查询、判断、协同或行动能力
    ↓
业务流程和岗位行为发生变化
    ↓
效率、风险、收入、成本或交付结果改善
    ↓
沉淀为可复用模型、数据、规则、动作和产品能力
```

任何一环断裂，都可能出现“模型质量很高但业务没有变化”。

#### 12.3 建立基线和反事实

在试点前记录：

- 当前流程步骤、参与角色和处理时长；
- 当前错误、漏判、返工和异常率；
- 当前人力、系统和外部服务成本；
- 当前风险损失、库存、交付或收入表现；
- 当前用户体验、信息获取和决策等待；
- 当前使用的替代方案及其限制。

价值评估应尽量建立反事实：如果不上本体，指标可能如何变化。可采用历史对比、分组试点、影子运行、专家盲评或同期对照，避免把正常业务波动全部归因于本体。

#### 12.4 明确价值机制

每个指标必须说明本体如何导致改善。例如：

| 目标结果 | 中间机制 | 可观察指标 |
| --- | --- | --- |
| 缩短供应中断响应 | 自动连接供应商、物料、库存、生产和订单 | 影响分析生成时间、覆盖率、人工查询步骤 |
| 降低关联交易漏判 | 统一主体身份并穿透控制关系 | 自动命中率、漏判率、人工复核量 |
| 降低付款风险 | 将合同、收货、发票、货权和审批证据关联 | 异常发现率、冻结和复核时长、损失避免 |
| 提高 Agent 可控性 | 通过对象权限和动作契约调用系统 | 越权率、错误动作率、人工接管和审计完整率 |

只有说明中间机制，才能在结果未达目标时定位是模型、数据、流程、采用还是外部环境问题。

#### 12.5 业务流程重设计

上线前应明确：

- 哪些人工查找、核对和汇总步骤被取消或缩短；
- 哪些判断由系统提供证据，人负责最终决定；
- 哪些动作可以自动或半自动执行；
- 异常、冲突和低置信度结果由谁处理；
- 用户拒绝建议时如何记录原因；
- 结果如何写回业务系统和形成闭环；
- 岗位职责、绩效和审批制度是否需要调整。

如果原流程完全不变，本体往往只是增加了一个新的查询界面，而不是改变业务能力。

#### 12.6 用户采用

采用管理至少包括：

- 目标用户分组和真实工作场景测试；
- 界面、解释和证据展示设计；
- 培训、操作手册和支持渠道；
- 业务负责人公开背书和制度嵌入；
- 使用率、留存、建议采纳和人工绕过监控；
- 对“不使用”原因进行分类：结果不可信、流程不匹配、性能、权限、习惯或激励；
- 将用户修改和拒绝理由回流到模型和产品。

强制使用不能替代可信性和可用性。高使用率也不等于产生价值，必须结合业务结果判断。

#### 12.7 成本和净价值

本体项目成本至少包括：

- 场景分析和业务参与；
- 数据授权、治理、身份和接入；
- 建模、评审和测试；
- 平台、模型、存储和计算；
- 应用集成和流程改造；
- 安全、合规和审计；
- 培训、采用和运营；
- 后续版本、数据漂移和消费者维护。

净价值应按“实现收益或风险避免 − 建设成本 − 持续运营成本”评估。共享资产被多个场景复用时，应同时记录避免的重复建设成本。

#### 12.8 试点后的四种决策

| 决策 | 条件 | 后续动作 |
| --- | --- | --- |
| **扩大** | 价值达到目标，质量稳定，复用潜力高 | 扩展对象、数据、用户或放权级别 |
| **固化** | 当前场景有价值，但复用范围有限 | 转入稳定运营，控制继续投资 |
| **调整** | 部分有效，但数据、流程或采用存在可修复问题 | 修改范围、价值机制或解决阻断因素 |
| **停止** | 价值不足、成本过高、风险不可控或更简单方案更优 | 归档资产、保留学习、停止扩张 |

#### 12.9 产品化与复用

一个场景资产只有满足以下条件，才应进入企业级产品或模板：

- 语义边界清晰，不依赖单个项目的隐含背景；
- 具有正式所有者、版本、文档和测试；
- 数据映射可以参数化或替换；
- 已在至少一个真实场景中验证；
- 安全和权限可以复用或配置；
- 消费接口和动作契约稳定；
- 有明确适用范围、限制和接入指南。

可复用资产包括：共享对象、领域模型、术语、身份规则、数据连接器、映射模板、能力问题、测试集、动作、工作台组件、AI 提示和评估集。

#### 12.10 成熟度模型

| 级别 | 特征 | 主要目标 |
| --- | --- | --- |
| **M1 项目化** | 单个试点，模型和数据依赖项目人员 | 跑通候选—认证—生产闭环 |
| **M2 可重复** | 有基本模板、角色、版本和测试 | 降低第二个场景的交付成本 |
| **M3 领域化** | 领域本体和数据契约由长期团队维护 | 形成领域共享资产和多场景复用 |
| **M4 企业化** | 共享核心、联邦治理、统一平台和跨域消费 | 支持企业级一致性和规模运营 |
| **M5 自适应** | 漂移监测、反馈回流、AI 辅助和价值优化常态化 | 持续演进并形成语义资产复利 |

企业不应为了追求成熟度等级提前建设所有平台能力。每一级都应由真实消费者和业务价值推动。

#### 12.11 方法卡

| 项目 | 内容 |
| --- | --- |
| **输入** | 价值假设、基线、生产数据、用户行为、运营成本和业务结果 |
| **核心活动** | 流程改造、采用管理、价值测量、归因、复盘和产品化评估 |
| **交付物** | 价值实现报告、流程变化说明、采用分析、成本收益、扩大/固化/调整/停止决策、复用资产包 |
| **主要角色** | 业务负责人对价值问责，产品负责人组织采用和复盘，财务或运营分析协助归因，平台团队沉淀复用资产 |
| **退出条件** | 业务价值和运营成本可解释，后续投资决策明确，资产有长期责任或完成归档 |

### 第 13 章 AI 辅助本体工程与本体驱动 AI

#### 13.1 两条相互独立但可以闭环的路径

企业本体与 AI 的结合包含两个方向：

1. **AI 辅助本体工程**：用大模型提高取证、抽取、对齐、文档、测试和评审效率；
2. **本体驱动 AI 消费**：用正式对象、关系、规则、权限和动作约束 AI 获取上下文和执行任务。

不能因为 AI 参与了建模，就自动认为模型可信；也不能因为 Agent 使用了本体，就认为其输出和行动一定正确。两条路径都需要独立评估和控制。

#### 13.2 AI 辅助本体工程管线

一个可复现的 AI 工程流程可以包括：

```text
任务与范围准备
  → 来源解析和证据切片
  → 术语、对象、关系、规则和动作候选抽取
  → 同义归一、实体聚类和冲突识别
  → 模型结构建议和数据映射建议
  → 证据绑定与置信信息
  → 自动结构校验和能力问题测试生成
  → 人工评审与修改
  → 差异回流到评估集、规则和提示模板
```

每次运行应记录：

- 输入来源及版本；
- 任务、提示和输出 Schema 版本；
- 使用的模型和参数；
- 生成时间和成本；
- 证据引用；
- 自动校验结果；
- 人工接受、修改和否决差异。

#### 13.3 AI 生成候选的质量控制

建议采用以下控制：

- 要求严格结构化输出，不接受只有自然语言的模型草稿；
- 每项候选绑定证据或明确标记为推断；
- 将抽取、归一、建模和验证拆成多个任务，减少一步式生成；
- 对高影响元素使用多源交叉验证；
- 对冲突和低置信度结果强制人工确认；
- 使用固定评估集比较模型、提示和版本变化；
- 检查遗漏，而不仅检查错误生成；
- 监控模型成本、延迟、稳定性和供应商依赖。

模型置信度不是业务可信度。最终可信性来自证据、规则、人工责任和生产验证的组合。

#### 13.4 本体为 AI 提供的能力

本体可以为 AI 应用和 Agent 提供：

- 统一业务术语和对象身份；
- 经过授权的对象级上下文；
- 跨关系、跨时间的事实路径；
- 可引用的来源、证据和数据质量状态；
- 正式指标、规则和状态转换；
- 可发现的工具和动作契约；
- 对象、属性、关系和动作级权限；
- 可审计的查询、推理和执行记录；
- 业务结果回流和持续评估。

这些能力能够显著降低 AI 自行猜测数据结构、口径和工具的空间，但不能消除模型错误、数据错误或不完整推理。

#### 13.5 Agent 运行模式

建议将 Agent 运行分为：

1. **信息检索型**：读取对象和证据，不执行动作；
2. **分析建议型**：组合事实、计算或生成建议，由人决策；
3. **流程协助型**：准备材料、创建草稿、发起审批或通知；
4. **可逆执行型**：在审批和补偿机制下写回；
5. **受限自治型**：在明确策略、额度、对象和时间边界内自动执行。

每个 Agent 需要独立身份、最小权限、工具白名单、预算、超时、停止条件和人工接管方式。

#### 13.6 AI 评估体系

评估应同时覆盖：

- **事实性**：结论是否由正确的数据和证据支持；
- **完整性**：是否遗漏关键对象、关系、约束和例外；
- **语义一致性**：是否遵守正式定义和口径；
- **工具正确性**：是否选择正确动作并传入正确参数；
- **权限合规性**：是否访问或执行超出授权的内容；
- **稳定性**：同类输入和版本变化下结果是否可接受；
- **业务效果**：是否改善目标决策或流程；
- **成本与延迟**：是否满足生产经济性和服务目标。

评估集应包含正常、边界、冲突、恶意输入和事故样例，并持续吸收人工否决和生产异常。

#### 13.7 模型、提示和工具版本治理

生产结果应能够关联：

- 本体版本；
- 数据和映射版本；
- 规则与动作版本；
- 模型和模型供应商版本；
- 提示、系统指令和输出 Schema 版本；
- 工具和接口版本；
- 权限策略版本。

任何一项变化都可能改变结果，因此需要通过评估、灰度和回滚管理，不能只对本体本身做版本控制。

#### 13.8 AI 不应承担的职责

以下职责不能交由大模型独立承担：

- 对正式业务语义和跨域冲突作最终裁决；
- 批准自身生成的模型或变更；
- 在没有明确授权的情况下决定数据用途；
- 对高风险、不可逆业务动作独立放权；
- 将无证据推断写成正式事实；
- 对业务结果、合规和事故承担组织责任。

#### 13.9 方法卡

| 项目 | 内容 |
| --- | --- |
| **输入** | 本体工程任务或 Agent 场景、数据和模型政策、评估集、工具和权限 |
| **核心活动** | AI 管线设计、结构化输出、证据绑定、评估、版本管理、工具和动作控制 |
| **交付物** | AI 任务说明、提示与 Schema、评估报告、Agent 权限与工具清单、运行与审计策略 |
| **主要角色** | 本体和 AI 工程团队实施，领域专家评审语义，业务负责人批准使用与放权，安全团队控制模型和工具风险 |
| **退出条件** | AI 结果可追溯、可评估、可限制和可接管，模型变化不会绕过生产治理 |


## 第五部分：端到端示例

### 第 14 章 供应商停产影响分析：从一个场景跑通完整闭环

> 本章为方法演示。企业背景、时间和指标均为示例参数，使用时应替换为真实数据和管理目标。

#### 14.1 场景背景

某制造企业的供应商、采购、物料、BOM、库存、生产计划和客户订单分布在多个系统中。当供应商发生停产、限产或物流中断时，采购、计划、制造和销售团队需要分别查询并人工拼接信息，才能判断：

- 哪些物料会在什么时间出现缺口；
- 哪些生产订单和客户订单会受影响；
- 影响金额、交期和客户优先级如何；
- 是否存在可用库存、在途采购或替代供应商；
- 应当由谁在什么时间前作出决策。

现有系统能够分别查看采购订单、库存和生产计划，但不能稳定表达完整的影响传导关系，也不能在同一时间语义和身份规则下给出可追溯结论。

#### 14.2 S0：场景选择与价值假设

##### 替代方案比较

| 方案 | 能解决什么 | 主要不足 |
| --- | --- | --- |
| 增加一张跨系统报表 | 汇总部分供应、库存和订单字段 | 难以持续处理身份、BOM 多层关系、时间传播和业务例外 |
| 在 ERP 内修改计划逻辑 | 改善特定计划参数或计算 | 不能统一外部中断信息和多个系统中的对象语义 |
| 建立数据集市 | 提供统一分析数据 | 仍需显式定义业务对象、关系、时间、规则和行动闭环 |
| 建设场景本体 | 统一对象身份和关系，支持影响路径、证据、规则和动作 | 需要跨团队语义评审、数据治理和持续运营 |

该场景不是因为“系统多”而选择本体，而是因为判断依赖多层对象关系、未来时间窗口、身份统一、规则和可追溯行动。

##### 价值假设

> 通过建立供应商—供应关系—物料—BOM—库存—生产订单—客户订单的统一对象模型，并将供应中断事件与计划时间连接，在供应商中断信息出现后自动生成可追溯的影响清单和替代建议，从而显著缩短影响判断时间、提高受影响订单识别覆盖率，并减少跨部门人工核对。

##### 示例基线和目标

| 指标 | 示例基线 | 示例目标 | 说明 |
| --- | --- | --- | --- |
| 首版影响清单生成时间 | 8 小时 | 30 分钟以内 | 从收到中断信息到形成首版清单 |
| 受影响订单识别覆盖率 | 无统一口径 | 95% 以上 | 以历史复盘和专家确认集为准 |
| 人工跨系统查询步骤 | 20 余次 | 降低 70% | 记录真实流程步骤 |
| 高优先级订单漏判率 | 无稳定统计 | 低于约定阈值 | 具体阈值由业务风险决定 |
| 结果可追溯率 | 部分 | 100% | 每项结论显示关系路径和来源 |

##### 停止条件

- 无法获得 BOM、库存和生产计划的关键数据；
- 物料或供应商身份在试点范围内无法稳定对齐；
- 历史回放无法覆盖主要中断类型；
- 业务团队不愿将影响分析嵌入实际响应流程；
- 简单数据修复和现有系统配置即可达到相同效果。

#### 14.3 S1：场景章程和能力问题

##### 关键决策

当某供应商在未来一段时间内无法按计划供货时，供应链负责人需要决定：

- 是否启动供应中断响应；
- 哪些订单需要重新排产或调整承诺；
- 是否启用库存、在途、替代物料或替代供应商；
- 哪些客户、金额和交期风险需要升级；
- 哪些动作必须立即执行。

##### 主要使用者

- 采购经理；
- 生产计划员；
- 供应链运营负责人；
- 销售交付负责人；
- 风险或应急管理人员。

##### 能力问题

1. 某供应商停产 72 小时，哪些采购订单不能按计划到货？
2. 这些采购订单对应哪些物料、工厂和生产订单？
3. 现有库存、在途和已确认到货能支撑到什么时间？
4. 多层 BOM 展开后，哪些上层产品和客户订单受到影响？
5. 影响金额、客户优先级、承诺交期和最晚决策时间分别是多少？
6. 是否存在已认证的替代供应商、替代物料或其他工厂产能？
7. 每个影响结论来自哪些数据、规则和时间假设？
8. 应当通知谁、发起什么审批或创建什么业务任务？

##### 试点范围

- 选择一个工厂、一个产品族和一组活跃供应商；
- 覆盖一至两级 BOM 关系；
- 只处理“供应商完全停产”和“关键物料延迟”两类事件；
- 输出影响分析和建议，不在首阶段自动更换供应商或修改生产计划。

##### 非目标

- 不重建整个 MRP 或 ATP 系统；
- 不治理企业全部历史供应商和物料数据；
- 不自动承诺新的客户交期；
- 不在试点阶段执行不可逆采购或生产动作；
- 不建设覆盖全部供应链风险的通用平台。

#### 14.4 S2：数据、证据与准备度

##### 数据资产

| 资产 | 主要内容 | 可能权威源 | 主要风险 |
| --- | --- | --- | --- |
| 供应商主数据 | 法定身份、状态、组织归属 | 供应商主数据系统 | 重复、名称变更、集团与法人混淆 |
| 供应关系 | 供应商、物料、工厂、份额、有效期 | 采购或寻源系统 | 一对多关系被简化、历史有效期缺失 |
| 采购合同与订单 | 数量、交期、状态、条款 | ERP 采购模块 | 状态口径不同、变更未同步 |
| 物料和 BOM | 物料身份、层级、用量、替代关系 | PLM/ERP | 版本、工厂和生效时间复杂 |
| 库存和在途 | 可用量、冻结量、地点、预计到货 | WMS/ERP/物流系统 | 时效、批次和质量状态 |
| 生产计划 | 生产订单、需求时间、产能 | APS/MES/ERP | 计划频繁变化、版本未保留 |
| 客户订单 | 产品、数量、交期、客户优先级 | 销售系统/ERP | 交期变化、订单拆分合并 |
| 替代供应商认证 | 认证范围、产能、有效期 | 供应商质量系统 | 认证状态和实际可供能力不一致 |
| 中断事件 | 停产范围、开始时间、预计恢复 | 人工登记、外部信息或供应商通知 | 信息不完整、可信度和更新时间不一 |

##### 证据规则

- 供应商中断是否真实，优先依据供应商正式通知、企业确认记录和持续更新；
- 供应关系是否有效，依据当前合同、采购资格和有效期，而不是仅看历史采购记录；
- BOM 展开使用指定工厂、产品版本和业务有效时间；
- 库存只计算可用于目标订单的可用库存，排除冻结、质检未通过或已预留部分；
- 替代供应商必须同时满足认证有效、物料适配、产能和交期条件。

##### 身份和时间规则

- 供应商使用全局供应商身份，同时保留法人、集团和来源系统标识；
- 物料按企业物料与工厂视图区分，避免同编码不同工厂属性混淆；
- BOM 关系保留版本和有效期；
- 供应中断事件记录发生时间、获知时间、预计恢复时间和最后更新时间；
- 影响计算记录使用的数据快照和计划版本。

##### 准备度问题及处理

| 问题 | 分类 | 处理方式 |
| --- | --- | --- |
| 部分供应商缺少统一法定标识 | 降级或阻断，视影响范围 | 在试点供应商中人工确认映射，低置信记录不自动合并 |
| BOM 只有当前版本，没有完整历史 | 降级 | 历史回放仅选择有快照的时间段，并记录限制 |
| 替代供应商产能更新不及时 | 标记 | 建议中显示数据时间和“需人工确认产能”状态 |
| 中断信息来源可信度不一 | 降级 | 使用来源等级和人工确认状态，不把传闻直接写为正式停产事实 |

#### 14.5 S3：候选本体建设

##### 核心对象

| 对象 | 身份与粒度 | 主要属性 |
| --- | --- | --- |
| **供应商** | 法人或受治理的供应实体 | 名称、状态、地区、风险等级 |
| **工厂** | 企业生产地点 | 地点、组织、能力范围 |
| **物料** | 企业物料及必要的工厂视图 | 编码、类别、单位、关键性 |
| **供应关系** | 供应商在特定条件下向工厂供应某物料 | 份额、价格、有效期、认证状态 |
| **采购订单行** | 采购订单中的最小供应承诺 | 数量、计划到货、状态、工厂 |
| **库存位置** | 某物料在地点和状态下的库存记录 | 可用量、冻结量、批次、时间 |
| **BOM 关系** | 父件在特定版本中使用子件 | 用量、损耗、替代组、有效期 |
| **生产订单** | 某工厂在指定时间生产一定数量产品 | 开始、完工、状态、优先级 |
| **客户订单行** | 客户订单中的具体交付承诺 | 产品、数量、交期、金额、优先级 |
| **供应中断事件** | 影响特定供应商、地点或物料的中断 | 类型、范围、开始、预计恢复、可信状态 |
| **影响评估** | 在指定数据和模型版本下的计算结果 | 影响程度、缺口、时间、金额、证据 |
| **响应任务** | 分派给角色的处理任务 | 类型、截止时间、状态、负责人 |

##### 核心关系

```text
供应商
  └─通过→ 供应关系
            ├─供应→ 物料
            └─面向→ 工厂

物料
  └─作为子件→ BOM 关系
                   └─组成→ 上层物料/产品

采购订单行 ─补充→ 物料库存
生产订单 ─消耗→ 物料
客户订单行 ─由→ 生产订单满足
供应中断事件 ─影响→ 供应关系/采购订单行
影响评估 ─引用→ 供应中断事件、库存、BOM、生产订单和客户订单
```

##### 事件、状态和规则

- 供应中断事件状态：待确认、已确认、更新中、已恢复、已关闭；
- 影响评估状态：待计算、已计算、已复核、已发布、已失效；
- 规则示例：仅计算中断窗口内预计到货且尚未完成的采购订单行；
- 规则示例：库存可用天数必须按物料、工厂、质量状态和已分配需求计算；
- 规则示例：替代供应商未完成认证时只能作为候选，不得自动推荐为可执行方案；
- 指标示例：预计缺口数量、最早缺料时间、受影响订单金额、客户优先级暴露。

##### 动作

- 生成影响评估；
- 请求采购确认中断范围；
- 通知生产计划员；
- 创建替代供应商评估任务；
- 发起订单优先级复核；
- 在达到相应放权等级后，创建可撤销的计划调整草案。

#### 14.6 数据映射示例

| 本体元素 | 来源 | 转换或规则 | 异常处理 |
| --- | --- | --- | --- |
| 供应商全局身份 | 供应商主数据 + 法定标识 | 法定标识强匹配，名称和地址辅助 | 冲突进入人工裁决队列 |
| 供应关系有效状态 | 合同、资格和采购组织数据 | 同时满足合同有效、资格有效和工厂范围 | 缺少任何关键条件则标记待确认 |
| 可用库存 | 库存明细 | 现存量减冻结、质检和已分配数量 | 数据过期则降低可信等级 |
| BOM 关系 | PLM/ERP BOM | 按产品版本、工厂和有效时间展开 | 缺少版本时不做历史推断 |
| 中断窗口 | 正式通知或人工确认 | 开始时间至预计恢复时间 | 来源未确认时只做情景模拟 |
| 受影响订单金额 | 客户订单行 | 受影响数量 × 订单口径金额 | 币种和含税口径必须显式 |

#### 14.7 语义契约示例：供应中断事件

| 字段 | 定义 |
| --- | --- |
| **名称** | 供应中断事件（Supply Disruption Event） |
| **正式定义** | 在特定时间窗口内，使已确认供应关系全部或部分无法按约定数量、地点或时间履行的事件 |
| **不包括** | 尚未影响已确认供应承诺的一般风险传闻；仅价格变化但不影响供货的事件 |
| **身份** | 事件来源 + 供应主体 + 影响范围 + 首次确认时间形成受治理标识 |
| **时间** | 发生时间、获知时间、预计恢复时间、最后更新时间分别记录 |
| **状态** | 待确认、已确认、更新中、已恢复、已关闭 |
| **关系** | 影响供应商、供应关系、物料、地点和采购订单行 |
| **证据** | 正式通知、内部确认记录、更新时间和责任人 |
| **质量要求** | 已确认状态必须至少有一项正式或经授权人工确认的来源 |
| **权限** | 供应链和风险角色可见；外部敏感原因按最小范围展示 |
| **消费者** | 影响分析服务、供应链工作台、通知和响应任务服务 |
| **已知限制** | 预计恢复时间可能频繁变化，所有影响结果必须显示计算时间和事件版本 |

#### 14.8 S4：认证过程

##### 典型评审结论

- 将“供应商停产”修改为更广义的“供应中断事件”，因为实际还包括限产、物流阻断和特定物料不可供；
- 将“供应商供应物料”从简单关系拆分为“供应关系”对象，以承载工厂、份额、认证和有效期；
- 否决“库存数量”单一属性，改为按地点、状态、时间和分配情况计算可用库存；
- 搁置自动推荐替代供应商，等待产能和认证数据契约完善；
- 增加“观察时间”，避免事后录入的信息被误认为当时已经可知。

##### 能力问题测试

| 测试 | 输入 | 预期验证 |
| --- | --- | --- |
| 单一物料中断 | 已知供应商、物料和 72 小时窗口 | 识别相关采购、库存和生产订单 |
| 多层 BOM 传播 | 子件影响上层产品 | 路径、数量和有效版本正确 |
| 库存足够 | 中断但库存覆盖需求 | 不将订单错误标记为缺料 |
| 数据过期 | 库存超过新鲜度阈值 | 结果显示警告并要求复核 |
| 未确认事件 | 仅有外部传闻 | 只进入情景模拟，不触发正式响应 |
| 替代供应商未认证 | 存在供应记录但认证失效 | 不作为可执行替代方案 |
| 历史回放 | 选定已知中断事件 | 输出与历史实际和专家判断进行比较 |

##### 认证退出条件

- 核心对象和关系的语义契约获批准；
- 试点数据映射和身份规则可重复运行；
- 关键能力问题在测试数据上可回答；
- 未解决的数据限制有显式降级方式；
- 消费工作台能够显示来源、路径、时间和质量；
- 首阶段动作仅限通知和任务创建，不执行不可逆业务变更。

#### 14.9 S5：历史回放和影子运行

##### 历史回放

选择若干已发生的供应中断案例，重建当时可获得的数据快照，并比较：

- 实际受影响订单与系统识别结果；
- 首次识别时间；
- 影响数量和金额误差；
- 漏判和误判原因；
- 当时不可获得、但事后才录入的信息；
- 专家判断和模型判断差异。

必须避免使用事后信息“穿越”回历史时点，否则会高估模型能力。

##### 影子运行

在真实中断信息到来时，本体系统与人工流程并行：

- 系统生成影响清单，但不直接改变计划；
- 人工团队独立完成原有分析；
- 比较时间、覆盖、差异和解释；
- 记录人工修改、拒绝和新增项；
- 识别问题来自模型、数据、流程还是界面。

#### 14.10 S6：生产运行和放权路径

| 阶段 | 本场景能力 | 控制措施 |
| --- | --- | --- |
| **L1 历史回放** | 计算历史事件影响 | 不连接生产动作 |
| **L2 影子运行** | 对实时事件生成内部结果 | 结果不进入正式流程 |
| **L3 辅助决策** | 向采购、计划和供应链负责人展示影响和建议 | 人工确认后发布响应 |
| **L4 可逆写回** | 创建通知、任务和计划调整草案 | 审批、幂等、可撤销和完整审计 |
| **L5 受限自动化** | 对低风险、规则明确的通知和任务自动执行 | 限定对象、额度、动作和时间；高风险决策仍由人批准 |

##### 生产工作流

```text
中断信息进入
  → 验证来源和事件状态
  → 识别受影响供应关系与采购订单
  → 计算库存、在途和需求覆盖
  → 展开 BOM 并连接生产与客户订单
  → 生成影响评估、路径和证据
  → 按优先级分派响应任务
  → 人工确认或批准动作
  → 结果写回并持续更新
  → 事件恢复后关闭和复盘
```

#### 14.11 生产监控

##### 模型和数据

- 供应商和物料身份匹配失败率；
- BOM、库存、订单和事件数据新鲜度；
- 关键映射和契约违约；
- 低置信度和人工裁决积压；
- 语义和源结构漂移。

##### 业务和使用

- 影响清单生成时间；
- 订单覆盖、误判和漏判；
- 建议采纳和人工修改；
- 响应任务完成时间；
- 用户绕过系统的比例和原因；
- 交付风险、加急成本或停线损失变化。

##### 运行和安全

- 查询和计算延迟；
- 动作成功、失败和补偿；
- 越权或异常批量查询；
- 回滚、降级和人工接管事件；
- 本体、数据、规则和模型版本关联完整性。

#### 14.12 价值验收

试点结束时不只展示模型图和查询演示，而应形成价值报告：

1. 与基线相比，影响判断时间是否缩短；
2. 覆盖、误判和漏判是否达到门槛；
3. 人工工作量减少在哪些步骤；
4. 哪些流程和岗位行为已经改变；
5. 用户是否持续采用，拒绝原因是什么；
6. 实际建设和运营成本是多少；
7. 哪些收益可以合理归因于本体；
8. 哪些数据和流程问题仍然限制价值；
9. 是否扩大到更多工厂、产品、供应商或动作；
10. 哪些资产可以进入领域或企业共享层。

#### 14.13 可复用资产

该场景成功后可以沉淀：

- 供应商、物料、工厂、订单等共享对象；
- 供应关系、BOM 和订单满足关系；
- 供应中断事件和影响评估语义契约；
- 身份、时间和库存可用性规则；
- 供应链能力问题和历史评估集；
- 数据连接器与映射模板；
- 影响分析工作台组件；
- 通知、任务和审批动作；
- 供应中断 Agent 的权限和评估集；
- 运营指标、告警和事故处理手册。

这些资产可以支持下一步场景，例如自然灾害影响、港口延误、供应商财务风险、质量召回和替代供应商规划，但每个新场景仍需重新建立价值假设和适用边界。

#### 14.14 典型失败点及控制

| 失败点 | 后果 | 控制方式 |
| --- | --- | --- |
| 直接复制 ERP 表结构 | 模型无法表达业务粒度和跨系统语义 | 从能力问题和正式对象身份出发建模 |
| 只关注供应商，不表达供应关系 | 无法区分物料、工厂、份额和有效期 | 将关系属性化为受治理对象 |
| 忽略时间版本 | 历史回放和未来影响计算错误 | 分离有效时间、记录时间和计划版本 |
| 库存口径过于简单 | 大量误判和错误建议 | 明确可用、冻结、质检和已分配规则 |
| 把传闻写成正式中断事实 | 触发不必要响应 | 事件状态和来源可信度分级 |
| 过早自动调整计划 | 放大错误影响 | 先回放、影子和辅助决策，逐动作放权 |
| 只交付影响分析界面 | 用户流程不变，价值有限 | 同步调整响应流程、任务和责任 |
| 不记录人工修改理由 | 无法改进模型和规则 | 将修改、证据和最终结果回流评估集 |

| **对象类型** | 具有稳定业务身份和生命周期的一类事物 |
| **实例** | 某一对象类型的具体业务实体或事实记录 |
| **属性** | 描述对象特征的值 |
| **关系类型** | 表达对象之间具有业务含义的联系 |
| **关联对象** | 当关系本身具有属性、时间、状态或生命周期时，将其建成独立对象 |
| **事件** | 在特定时间发生并可能改变对象状态的业务事实 |
| **状态** | 对象在其生命周期中的阶段或条件 |
| **业务规则** | 对事实进行约束、分类、计算或决策的确定性逻辑 |

| **数据契约** | 对数据结构、语义、质量、时效、责任、变更和安全的可验证承诺 |

| **溯源** | 记录某项模型或事实由谁、在什么活动中、基于什么来源生成或修改 |
| **身份解析** | 将多个系统中的同一业务对象对齐到统一身份的过程 |
| **有效时间** | 事实在业务世界中成立的时间 |
| **记录时间** | 事实进入或被修改于信息系统的时间 |
| **候选本体** | 尚未完成正式语义认证的模型草案和相关证据包 |
| **认证本体** | 已经完成语义、数据、结构和消费者评审的正式版本 |
| **生产本体** | 已被生产应用或流程消费，并具备监控、权限、审计和回滚的本体版本 |
| **语义差异** | 两个版本在定义、身份、关系、规则、动作和治理方面的业务含义变化 |
| **质量闸门** | 进入下一生命周期状态前必须满足的验证条件 |
| **渐进放权** | 从历史回放、影子运行到受限自动化，逐步增加业务影响和行动权限 |
| **漂移** | 源结构、数据分布、业务语义或消费方式相对已认证模型发生变化 |
| **共享核心** | 在多个业务域中稳定复用的企业级对象和语义 |
| **领域本体** | 由特定业务域拥有和维护的专业对象、关系、规则和动作 |
| **场景视图** | 为一个业务场景组合共享与领域对象形成的消费视图，不重新复制正式定义 |

### 附录 E：常见反模式总表

| 反模式 | 表现 | 修正方向 |
| --- | --- | --- |
| **平台先行** | 先采购技术和建设底座，后寻找场景 | 从业务问题、价值和消费者开始 |
| **一次性企业级大模型** | 试图先覆盖所有领域和概念 | 由场景驱动，逐步形成共享核心 |
| **数据库表即本体** | 对象粒度和关系完全照搬物理结构 | 以业务身份、生命周期和能力问题建模 |
| **知识图谱即本体** | 有大量节点和边，但没有正式定义、约束和责任 | 增加语义契约、版本、质量和治理 |
| **证据单一排序** | 默认数据库永远比制度或专家更权威 | 按待确认问题类型选择权威证据 |
| **锚定主表即可信** | 找到表字段后跳过业务认证 | 分离实现证据和语义认证 |
| **AI 自动建模即完成** | 大模型输出直接进入正式模型 | AI 生成候选，人类评审并承担责任 |
| **固定总分治理一切** | 用一个健康分掩盖关键阻断风险 | 分层质量和场景化门槛 |
| **无消费者建模** | 模型持续扩展但没有应用使用 | 每项认证资产必须有场景和消费者 |
| **只读演示停在 PoC** | 查询效果好，但没有流程、责任和价值闭环 | 设计采用、动作、运营和价值实现 |
| **一次性全面放权** | 未经回放和影子运行直接自动执行 | 按动作逐级放权 |
| **回滚万能论** | 认为回滚模型就能撤销业务影响 | 对写回动作设计补偿和人工处置 |
| **治理委员会替代所有者** | 所有问题都上会，但日常无人维护 | 为对象、数据、版本和价值指定具体所有者 |
| **只看对象数量** | 用模型规模评价成绩 | 评价复用、使用、质量、运营和业务结果 |
| **忽视采用** | 系统上线但用户继续走旧流程 | 将流程、培训、激励和反馈纳入交付 |

## 结语

企业本体的价值不在于建立一张规模庞大的模型图，而在于把企业中原本“定义不一致、关系串不起来、历史追不到、规则说不清、AI 不敢执行”的业务问题，转化为可被组织共同理解、可由数据支撑、可通过系统消费、可安全行动并可持续治理的语义资产。

一套有效的企业本体方法必须同时具备五个条件：

1. **从业务价值开始**，而不是从技术平台或抽象建模开始；
2. **由证据和显式设计决策支撑**，而不是依赖未经记录的个人判断；
3. **经过正式认证和分层质量验证**，而不是把候选模型直接投入生产；
4. **通过渐进放权、权限、监控和回退进入真实流程**，而不是停留在演示；
5. **由明确组织长期拥有，并通过价值复盘和复用形成资产复利**。

因此，企业本体建设的正确路径不是“先建完整本体，再寻找价值”，而是：

> **选择一个值得解决的业务问题，建立可验证的价值假设；以能力问题定义边界，以数据和证据建设候选模型；通过语义契约、评审和测试将其认证；在历史回放和影子运行中验证，通过渐进放权进入生产；最后用业务结果决定是否扩展，并把经过验证的对象、关系、规则、动作和运营经验沉淀为下一场景可复用的企业资产。**

这条路径使本体从概念研究转变为企业可以投资、交付、审计、运营和持续复用的业务能力。
