# DRP 平台产品功能与本体挖掘结合方案（阅读版）

> 版本：v1.1-read  
> 日期：2026-08-12  
> 定位：面向国资穿透式监管的产品与技术方案阅读版，用于统一产品边界、技术架构、Ontology 建模方法、风险分析链路、数据治理、安全治理、实施路线与验收口径。
>
> 本文坚持“源业务系统只读接入、事实与语义分离、Ontology 统一业务对象、分析能力分层、证据可追溯、关键结论人工复核”的总体原则。DRP 可以维护自身的模型、规则、线索、任务、报告和审计记录，但不向 ERP、财务、司库、采购、合同、投资、项目、OA 等源业务系统回写业务数据。
>
> 需要进入属性字典、规则 DSL、接口契约、部署拓扑、WBS 等实现级细节时，使用 [[DRP 平台产品功能与本体挖掘结合方案（详细设计版）]]。政策条款、监管口径和客户数据边界在项目实施时仍应以正式文件与客户一手环境为准。

## 0. 阅读说明

### 0.1 文档用途

本文不是单纯的产品功能清单，也不是某一种数据库或图技术的实现说明，而是用于回答四类问题：

1. DRP 平台应该建设哪些监管能力，哪些能力应继续由既有业务系统承担；
2. 数据平台、Ontology、规则、图分析、AI 与监管应用之间如何分工；
3. 如何从源数据形成可验证的监管线索、证据链和监管闭环；
4. 如何以可控范围完成试点，并通过版本、权限、评测和审计逐步扩展。

### 0.2 建议阅读路径

- 管理者/决策者：第 1、2、9、10、11 章；
- 产品/架构/研发：第 2、3、5、6、7 章；
- 实施/项目经理：第 4、8、9、10 章；
- 本体工程师：重点阅读 3.5、5、7.4、12、13；
- 需要进入实现级设计时：转入详细设计版，不在阅读版中堆叠 API、DDL 与部署参数。

### 0.3 核心边界

本文中的“只读”专指**源业务系统业务数据只读**：

```text
源业务系统 / 外部数据源
        ↓ READ ONLY
数据接入与数据平台
        ↓
Ontology 语义与对象查询
        ↓
规则 / 风险模型 / 图分析 / 检索 / AI
        ↓
监管分析与协同
        ↓
监管应用
```

DRP 自身仍然需要写入和维护：本体模型元数据、映射配置、索引状态、规则版本、风险线索、核查记录、整改跟踪、报告、用户配置和审计日志。上述写入均发生在 DRP 自身，不改变源业务系统中的交易、审批、付款、合同或项目状态。

官方宣贯口径的“五大升级方向”：财务管理体系化、财务系统集成化、财务信息数字化、财务监督智能化、财务转型一体化。

### 1.2 现状痛点（来自公开报道与行业解读，未逐项一手核验）

1. 系统林立、数据孤岛：同一集团多个 ERP/业务系统并行，同一物资、客户、账户在不同系统标识不一致。
2. 业财脱节：业务数据与财务数据不能自动关联，报表需要人工拼接。
3. 数据质量不足：部分企业合同数据完整率不足三成；银企直联覆盖率不足；参股企业“投而不管”。
4. 监管盲区：三级以下子公司、境外单位、SPV 长期处于“看得见报表、看不见过程”的状态。
5. 事后监管：依赖逐级上报与抽样审计，发现问题时损失已经形成。

### 1.3 穿透式监管的本质

穿透不是“画更深的图”，而是连续回答七个问题：

1. 谁在做：名义主体、实际控制人、最终受益人、一致行动人、经办人/责任人；
2. 和谁做：交易对手、关联方及其背后的控制关系；
3. 做了什么：投资、采购、融资、担保、借款、资产处置等行为；
4. 钱怎么走：预算、合同、发票、付款、收款、账户、最终资金去向；
5. 权责如何传导：发起、审批、授权、执行、监督、责任；
6. 违反什么要求：触发的制度、监管规则、阈值、禁止性规定、风险模式；
7. 证据在哪里：支持结论的系统记录、文件条款、时间快照、人工核查结果。

### 1.4 本方案边界与定位

本方案将 DRP 定位为**穿透式监管的数据、语义、分析与协同体系**，而不是 ERP、财务、司库、采购、合同、投资或 OA 的替代系统。

推荐建设边界：

1. **监管语义与 Ontology 能力**：把异构数据组织为统一的 Object Types、Properties、Link Types、Interfaces 与可查询 Objects；
2. **穿透分析能力**：基于 Object Sets、Search Around、规则、图分析、OLAP、检索和风险模型完成跨层级、跨系统、跨时间分析；
3. **监管协同能力**：把分析结果转化为线索、核查、证据包、整改跟踪和监管报告；
4. **本体挖掘与治理方法**：通过 G0–G5/C0–C3 将系统证据转化为受治理、可版本化的语义模型；
5. **只读集成能力**：以 ETL/ELT/CDC/API/文件等方式读取源系统数据，不将监管分析结果直接写回源系统。

不纳入本方案的职责：

- 替代 ERP 等系统执行交易和审批；
- 由 AI 自动认定违规事实或责任；
- 由 Ontology 替代 MDM、数据湖、数仓、图算法或规则引擎；
- 由 DRP 直接冻结付款、终止合同或修改源系统业务状态。

建设上优先采用“**单场景试点 + 平台化复用**”：先选一个数据基础较好、证据链明确的监管场景形成端到端闭环，再复用统一对象、关系、规则治理和监管协同能力扩展到其他业务域。

## 2. 总体架构

### 2.1 八层分层架构

![[DRP 软件功能架构.drawio.png]]

平台自上而下划分为八个纵向层级：

1. **用户与入口层**：身份、门户、工作台、搜索、消息与多端访问；
2. **监管应用层**：驾驶舱、穿透监管、风险作业、AI 监管、报送与决策支持；
3. **风险分析与监管协同层**：风险发现、解释、线索、核查、证据、整改跟踪、报告与责任事实链；
4. **AI / 规则 / 分析智能层**：规则引擎、风险模型、图分析、全文/语义检索、OLAP、AI Agent；
5. **Ontology 本体层**：统一业务对象、属性、关系、接口、对象集与查询语义；
6. **数据平台与治理层**：多模数据底座、主数据、数据标准、质量、元数据、血缘、资产目录与数据服务；
7. **数据接入与源系统层**：以只读方式接入 ERP、司库、财务、合同、采购、投资、项目、HR、OA 及外部数据；
8. **基础设施层**：计算、存储、网络、容器、消息、缓存、备份容灾和可观测性。

横向由三类保障体系覆盖全部层级：

- 运维保障；
- 安全保障；
- 合规与治理。

### 2.2 核心数据与分析链路

```text
内部业务系统 / 外部数据源
          ↓ READ ONLY
ETL / ELT / CDC / API / 文件交换
          ↓
数据湖 / 数仓 / 关系数据库 / 搜索索引 / 图计算数据
          ↓
数据标准 / MDM / 元数据 / 数据质量 / 血缘
          ↓
Backing Datasources / Property Mappings
          ↓
Ontology
  ├─ Object Types / Properties / Shared Properties
  ├─ Link Types / Interfaces / Object Type Groups
  └─ 只读 Object Index / Object Service
          ↓
Objects / Object Sets / Filters / Ordering / Aggregations / Search Around
          ↓
Rules / Risk Models / Graph / Search / OLAP / AI Agent
          ↓
风险分析 / 风险解释 / 监管线索 / 证据包 / 核查协同
          ↓
穿透监管 / 驾驶舱 / AI监管 / 报告与决策支持
```

### 2.3 关键设计原则

1. **源系统只读**：DRP 从源系统获取事实，不改变源系统的交易、审批或业务状态；
2. **事实、语义、判断分离**：数据平台保存事实，Ontology 组织语义，规则/模型进行判断，监管人员完成最终复核；
3. **上层面向 Object，不面向表**：应用、Agent 和规则优先通过统一对象查询接口访问业务语义；
4. **Link 驱动穿透**：一跳业务导航优先由 Link Type + Search Around 表达，复杂多跳算法由图分析层承担；
5. **Object Set 驱动分析**：监管分析通常面向“高风险企业集合、异常付款集合、大额合同集合”，应以可复用对象集表达；
6. **证据闭环**：线索必须能够回溯到原始记录、制度条款、数据来源、时间状态和人工核查记录；
7. **确定性逻辑优先**：金额、日期、权限、阈值、身份强匹配等用确定性逻辑；AI 用于抽取、语义理解、辅助解释和报告生成；
8. **版本一切**：Ontology、映射、索引配置、规则、模型、指标和数据契约均可追踪版本；
9. **最小必要权限**：模型权限、对象数据权限、功能权限和导出权限分离治理；
10. **可降级与可回放**：实时链路失败时可退化到 T+1/批处理；规则和模型变更可以历史回放验证。

### 2.4 各层责任边界

| 层/系统 | 负责 | 不负责 |
| --- | --- | --- |
| 源业务系统 | 交易、核算、合同、审批、项目、人员等业务事实 | 跨系统监管语义与监管分析 |
| 数据接入层 | 安全、稳定、只读获取数据 | 定义业务语义、判断风险 |
| 数据平台与治理 | 存储、加工、标准、MDM、质量、血缘、高性能数据计算 | 定义统一业务对象、作出监管结论 |
| Ontology | Object/Property/Link/Interface 等语义定义及对象查询表示 | MDM、复杂图算法、风险规则、工作流、业务写回 |
| 规则/风险模型 | 识别可能的异常、风险模式与阈值命中 | 直接认定违规事实 |
| 图分析 | 多跳路径、控制链、社区、环路和复杂关联分析 | 取代 Ontology 的业务语义定义 |
| AI Agent | 理解问题、调用受控工具、组织解释和报告 | 绕过权限直接查库、替代事实查询、自动定性 |
| 监管协同 | 线索、核查、证据、整改跟踪、报告 | 修改源业务状态 |
| 监管应用 | 面向最终用户组合和呈现监管能力 | 重复建设底层数据与语义能力 |

### 2.5 建设模式适配

| 客户模式 | 推荐嵌入方式 |
| --- | --- |
| 统建 | 作为集团统一 DRP 能力，复用统一身份、数据平台和治理体系 |
| 集成 | 通过只读 API/数据交换接入集团数据枢纽，子企业业务系统保持不变 |
| 混合 | 核心域统一接入，非核心域通过标准接口逐步纳管，Ontology 与规则治理保持统一 |

## 3. 逐层功能详述

### 3.1 用户与入口层

#### 3.1.1 角色与典型任务

| 角色 | 典型任务 | 核心入口 |
| --- | --- | --- |
| 集团监管人员 | 查看全级次风险、穿透对象关系、处理线索、发起核查 | 监管工作台、穿透分析 |
| 领导决策 | 查看集团态势、重点风险、趋势与重大事项 | 监管驾驶舱 |
| 企业用户 | 查看本企业事项、补充材料、反馈核查与整改情况 | 协同工作台 |
| 审计/纪检/专项检查 | 调阅授权范围内证据、复核线索、查看责任事实链 | 专项视图、证据包 |
| 风控/规则工程师 | 维护规则、阈值、评测集与发布版本 | 规则中心 |
| 数据管理员 | 数据标准、质量、主数据、血缘与授权 | 数据治理台 |
| 本体工程师 | 管理 Object Types、Link Types、Mappings、版本与权限 | Ontology Manager |
| 系统管理员 | 用户、系统配置、接口、运行状态 | 管理台 |

系统管理员不应因技术管理职责天然获得所有敏感业务数据访问权限。

#### 3.1.2 统一门户

- SSO，可对接 LDAP/AD、OIDC/OAuth2、SAML 等企业身份体系；
- 统一工作台、统一待办、统一消息与个人收藏；
- 全局搜索覆盖企业、项目、合同、付款、供应商、线索、制度和报告；
- 根据组织、角色、数据域、敏感级别动态控制菜单和数据可见性；
- PC 负责复杂分析，移动端负责消息/待办/轻查询，大屏负责态势展示。

#### 3.1.3 对象全景与监管工作台

推荐围绕 Object 构建统一对象全景页，例如：Enterprise 360、Project 360、Contract 360、Supplier 360。页面应包含 Properties、Links、相关指标、相关线索、证据入口和历史时间切片，并支持继续 Search Around。

所有重要指标和风险数字必须能够下钻到对象、关系和原始证据，不允许只有不可解释的汇总值。

### 3.2 监管应用层

监管应用层只承载监管用途，不复制建设 ERP/司库/采购/合同等源业务系统。核心模块包括：

| 模块 | 主要能力 |
| --- | --- |
| 监管驾驶舱 | 集团态势、风险态势、指标趋势、重点企业/项目、穿透总览 |
| 组织股权穿透 | 企业层级、持股、控制链、最终受益人、交叉持股、异常控制 |
| 资金穿透 | 付款方、账户、收款方、合同、项目、供应商、资金路径与异常 |
| 采购招投标穿透 | 采购需求→招标→投标→中标→合同→验收→付款全链分析 |
| 合同穿透 | 预算/项目/采购/合同/补充协议/发票/验收/付款关联分析 |
| 投资穿透 | 立项、尽调、决策、出资、投后、退出及控制权分析 |
| 三重一大穿透 | 事项、会议、表决、审批、授权、执行和相关合同/项目/资金 |
| 供应商/客户穿透 | 股东、实控人、高管、关联企业、交易历史、外部风险 |
| 项目穿透 | 立项、预算、采购、合同、付款、进度、验收、决算 |
| AI 监管应用 | 自然语言查询、风险解释、材料摘要、报告生成 |
| 报送与决策支持 | 报送模板、校验、专题分析、经营/对标分析 |

监管页面应围绕“从汇总到对象、从对象到关系、从关系到原始事实”的路径设计，而不是只建设静态大屏。

### 3.3 风险分析与监管协同层

该层承担“分析结果 → 可管理监管事项”的转换，避免规则、模型、AI 直接把输出当成业务结论。

标准链路：

```text
风险发现
  ↓
预警归一与去重
  ↓
风险分析与解释
  ↓
监管线索
  ↓
人工核查 / 补充材料
  ↓
确认 / 驳回 / 升级
  ↓
整改跟踪 / 专项移交 / 监管报告
  ↓
复核销号与反馈
```

核心能力：

- **风险发现**：接收规则、模型、图分析、外部风险与 AI 辅助分析结果；
- **预警归一**：统一风险对象、时间、等级、来源、版本，执行聚合与去重；
- **风险解释**：给出命中规则、指标、关系路径、时间线和证据引用；
- **线索管理**：线索生命周期、分派、优先级、状态、SLA；
- **核查管理**：核查对象、问题、人员、过程、结论及补充材料；
- **证据包管理**：证据来源、哈希、时间、版本、访问授权和导出审计；
- **整改跟踪**：记录整改责任、期限、反馈和复核状态；
- **责任事实链**：恢复事项→决策→合同→付款→人员等事实关系，供有权人员认定；
- **报告**：自动汇聚事实与证据形成可人工编辑、可审计的监管报告。

DRP 可以管理自身线索和协同任务，但任何“停止付款、终止审批、修改合同”等业务动作应由源业务系统及其既有授权流程执行。DRP 只提供风险升级、处置建议和事实依据。

#### 3.3.1 线索输出 Schema

| 字段 | 说明 |
| --- | --- |
| 线索编号 | 全局唯一 |
| 风险摘要 | 一句话说明 |
| 风险对象 | Object Type + Primary Key |
| 命中规则及版本 | Rule ID + Version |
| 穿透路径 | Objects + Links + 时间 |
| 时间线 | 相关事件序列 |
| 涉及金额 | 货币、期间与口径 |
| 原始证据清单 | 证据编号及来源 |
| 缺失数据 | 影响判断的数据缺口 |
| 风险等级/置信度 | 模型分级与人工分级分开记录 |
| 建议核查动作 | 下一步核查建议 |
| 人工复核结论 | 确认/驳回/补充/升级 |

### 3.4 AI / 规则 / 分析智能层

#### 3.4.1 规则引擎

规则至少包含：适用范围、触发方式、目标 Object/Object Set、穿透路径、时间窗口、指标/阈值、排除条件、所需证据、风险等级、人工复核要求、来源条款与版本。

规则生命周期：制度条款 → 业务规则稿 → 技术规则 → 测试用例 → 历史回放 → 评审发布 → 运行监控 → 调整/退役。

#### 3.4.2 风险模型

用于异常检测、关联风险、综合评分和趋势预测。模型输出是风险信号，不是监管事实；必须记录模型版本、输入特征口径、评测结果和解释信息。

#### 3.4.3 图分析

| 算法类型 | 用途 |
| --- | --- |
| 多跳路径搜索 | 跨多类关系查找关联路径 |
| 控制权累积 | 穿透实际控制与最终受益关系 |
| 社群/连通分量 | 识别隐藏关联网络 |
| 环路检测 | 循环持股、担保链、资金闭环 |
| 中心性 | 识别关系网络中的关键节点 |
| 相似模式 | 识别围标、异常交易等相似关系模式 |

Ontology 的 Link Type 负责定义业务关系语义；复杂图算法属于本层，不应被包装为新的 Ontology primitive。

#### 3.4.4 检索与 OLAP

- 全文检索：合同、制度、招标文件、报告、监管材料；
- 语义检索：相似案例、相近条款和文档；
- OLAP：聚合、趋势、多维分析和对标；
- 即席分析：授权分析人员组合 Object Set、指标和维度进行临时分析。

#### 3.4.5 AI Agent

AI Agent 应遵循“**先理解 Ontology，再调用受控工具，再生成解释**”的方式：

```text
自然语言
  ↓
业务意图 / 对象 / 时间 / 范围
  ↓
Object Search / Object Sets / Search Around
  + Rules / Graph / OLAP / Search
  ↓
结构化事实与证据
  ↓
解释 / 摘要 / 报告
```

禁止让 AI 绕过 Ontology 和权限边界直接面向全部数据库自由生成 SQL。关键输出必须标注模型版本、提示模板版本、输入摘要与证据引用；AI 只能形成候选、线索、疑点和解释，不自动输出“违规事实”。

### 3.5 Ontology 本体层（核心语义层）

Ontology 是连接底层事实数据与上层监管应用的统一业务语义层。其核心目标不是“把所有数据放进图数据库”，而是让上层能够用一致的业务对象、属性、关系和对象集访问数据。

本 DRP 采用 **Palantir Ontology 概念体系的只读子集**：模型元数据可治理和发布，业务 Object 数据由只读数据源及索引产生，不实施 Action Types、Actions、Ontology Edits 或源业务写回。

#### 3.5.1 Ontology Manager

Ontology Manager 管理以下核心语义资源与元数据：

| 能力 | 定义与 DRP 用法 |
| --- | --- |
| Object Types | 现实世界实体或事件的模式定义，例如 Enterprise、Contract、Payment |
| Properties | Object Type 的业务属性 |
| Shared Properties | 多个 Object Type 共用的 Property 元数据，用于统一定义和治理 |
| Link Types | 两类 Object 之间关系的模式定义，支持双向导航 |
| Interfaces | 跨多个 Object Type 约束共同能力/属性的语义契约 |
| Object Type Groups | 用于分类、检索和管理 Object Types，不表达继承层级 |
| Backing Datasources | Object Type 的底层数据来源 |
| Property Mappings | Property 与数据源字段之间的映射 |
| Primary Key | Object 实例稳定且唯一的标识 |
| Title Key | 对象在人机界面中的主要展示属性 |
| API Name | 稳定的程序访问名称 |
| Status / Metadata | 生命周期、描述、可发现性、所有者等治理信息 |
| Permissions | Ontology resource 权限与 Object 数据权限分离控制 |

Object Type 不应只理解为“实体表”。对于具有稳定身份、独立生命周期且需要单独查询的业务事件，例如 Payment、Meeting、ApprovalEvent，也可以作为 Object Type；反之，简单关系优先建模为 Link Type，不为追求“对象数量”把每条关系都实体化。

#### 3.5.2 Objects、Object Sets 与查询

上层应用的统一查询入口应围绕 Objects 与 Object Sets：

- **Object**：Object Type 的实例；
- **Object Search / Search Objects**：按类型和 Property 查询对象；
- **Object Set**：满足过滤条件的一组 Objects，可复用为监管对象集合；
- **Filters**：按属性和条件筛选；
- **Ordering**：按风险、金额、时间等排序；
- **Aggregations**：Count、Sum、Group By 等对象集聚合；
- **Search Around**：从一个 Object/Object Set 沿 Link Type 导航到关联对象。

例如：

```text
高风险企业 Object Set
       ↓ Search Around
相关合同 Object Set
       ↓ Search Around
相关付款 Object Set
       ↓ Search Around
交易对手 / 股东 / 人员
```

“Ontology Query”在本文中仅表示基于 Objects/Object Sets 的查询模式，不定义为新的 Ontology resource。

#### 3.5.3 Link Types 与穿透边界

Link Type 是穿透式监管的核心语义机制。建议优先表达具有稳定业务含义的一跳关系，例如：

| Link Type 语义 | 典型两端 | 时间语义 |
| --- | --- | --- |
| owned by / owns | Enterprise ↔ Enterprise/Person | 持有区间 |
| controlled by | Enterprise ↔ Enterprise/Person | 控制区间 |
| party to | Contract ↔ Enterprise | 合同有效期 |
| paid through | Payment ↔ BankAccount | 交易时点 |
| based on | Payment ↔ Contract/Invoice/Acceptance | 单据时点 |
| belongs to | BankAccount ↔ Enterprise | 账户有效区间 |
| related to project | Contract/Payment ↔ Project | 业务有效期 |
| approved by | ApprovalEvent ↔ Person/OrgUnit | 审批时点 |

Link 本身首先表达“两端 Object 之间存在某种业务关系”。关系来源、有效时间和证据应能够回溯到对应的 backing datasource。若关系本身具有需要独立查询和治理的重要属性或生命周期，例如持股比例、出资额、生效/失效日期、控制依据等，优先将该关系建模为中间关系 Object（如 `EquityHolding`、`ControlRelationship`），再通过 object-backed links 连接两端 Object，而不是把复杂业务属性隐含在普通 Link 中。复杂控制权累积、社区发现、环路检测等仍由图分析层执行。

#### 3.5.4 只读 Object Index 与对象服务

“只读”不意味着上层每次查询都直接扫描源系统，也不意味着 Ontology 完全不需要对象索引。为保证 Object Search、Filter、Aggregation 和 Search Around 的性能，推荐采用：

```text
源业务系统
   ↓ READ ONLY
数据平台
   ↓
Backing Datasource / Property Mapping
   ↓
只读 Object Index / Object Service
   ↓
Object Set Service / API / SDK
```

Object 索引是面向查询的派生表示，不是业务主数据的第二主系统。底层事实的权威来源仍由源系统与数据平台管理。

#### 3.5.5 Ontology API 与 SDK

对上层应用提供稳定的只读语义访问接口：

- 获取 Object Type/Link Type 元数据；
- Get/List/Search Objects；
- 加载和聚合 Object Sets；
- Search Around；
- 获取对象 Properties 和 Links；
- 按权限访问对象数据。

可提供 Java、Python、TypeScript 或 OpenAPI SDK，使应用代码面向 `Enterprise`、`Contract`、`Payment` 等业务类型，而不是直接依赖底层表名。

#### 3.5.6 本体挖掘工厂 G0–G5

| 阶段 | 输入 | 处理 | 输出 | 门禁 |
| --- | --- | --- | --- | --- |
| G0 资产登记 | 系统、数据源、文档、场景范围 | 登记资产与授权 | 资产清单、能力问题 | 关键资产缺失明确 |
| G1 证据提取 | DDL/API/代码/文档/样本 | 按坐标提取事实 | 坐标化证据 | 证据可定位 |
| G2 语义净化 | 证据、术语冲突 | 同义合并、异义拆分 | 术语表、争议项 | 争议有记录 |
| G3 候选建模 | 术语与证据 | Object/Property/Link/Interface 候选建模 | 候选卡、映射草案 | 候选有证据 |
| G4 评审包 | 候选、映射、质量信息 | lint、覆盖、影响检查 | 评审包 | 质量门禁通过 |
| G5 反馈回收 | 专家裁决 | 归档差异与原因 | 反馈与改进项 | 裁决完整 |

#### 3.5.7 本体认证 C0–C3

| 阶段 | 核心内容 |
| --- | --- |
| C0 逐项裁决 | accepted / accepted-with-change / merged / split / rejected / deferred |
| C1 语义与数据契约 | 定义、Primary Key、Backing Datasource、Property Mapping、时间/质量要求 |
| C2 权限与影响评审 | 模型权限、对象数据权限、破坏性变更影响、查询兼容性 |
| C3 版本发布 | 版本、发布日期、适用范围、索引状态、回滚点 |

#### 3.5.8 DRP 业务 Object Type 组织方式

标准监管对象、行业扩展对象和企业扩展对象是 **DRP 的模型治理分类**，不是三种 Palantir Ontology resource type。可通过 Object Type Groups 组织，但 Group 仅用于分类和发现，不提供继承或自动关系。

候选业务 Object Types 可包括：

- 主体：Enterprise、Person、OrgUnit、FinancialInstitution、SPV；
- 关系事件/关系对象（按需）：EquityHolding、ControlRelationship、EmploymentAssignment；
- 业务：Project、Contract、Procurement、Investment、Asset；
- 财务资金：BankAccount、Payment、Invoice、Voucher、Guarantee；
- 治理事件：Meeting、ApprovalEvent、AppointmentEvent；
- 监管：RiskClue、RegulatoryCase、RemediationTask、EvidencePackage。

是否建成 Object Type 由“是否具有稳定身份、独立生命周期、是否需要被单独查询/关联/授权”决定，而不是按名词机械建模。

#### 3.5.9 不属于 Ontology primitive 的能力

以下能力仍是 DRP 的重要组成，但必须保留在各自层级：

```text
实体身份归一 / MDM      → 数据治理层
监管指标与规则          → 规则/分析层
风险评分                → 风险模型
复杂图算法              → 图分析
全文 / 向量检索         → 检索层
工作流 / 核查 / 整改    → 监管协同层
报送                    → 监管应用层
AI Agent                → AI 分析层
```

### 3.6 数据平台与治理层

数据平台负责事实数据的保存、加工、治理和高性能计算。推荐分为“多模数据底座”和“数据治理”两部分。

#### 3.6.1 多模数据底座

| 能力 | 主要用途 |
| --- | --- |
| 数据湖/湖仓 | 原始数据、历史明细、文件、半结构化数据 |
| 数仓/OLAP | 明细、汇总、主题、指标计算与多维分析 |
| 关系数据库 | DRP 配置、线索、任务、报告、审计等事务数据 |
| 图数据/图计算 | 多跳关系计算、控制链、社区与环路分析 |
| 搜索引擎 | 全文检索、对象搜索加速、文档索引 |
| 流式处理 | CDC、事件流、低延迟规则触发 |

不要求所有 Object 实例永久复制到独立图数据库。是否使用图存储、关系数据库、搜索索引或对象索引，应根据查询模式、规模、时效和成本选择。

#### 3.6.2 数据治理

| 能力 | 功能点 |
| --- | --- |
| 数据标准 | 编码、字段、口径、命名、值域、时间语义 |
| MDM/身份解析 | 企业、人员、账户、项目、合同等跨系统身份统一 |
| 元数据 | 表/字段/接口/对象/指标元数据 |
| 数据质量 | 完整性、及时性、一致性、准确性、唯一性 |
| 数据血缘 | 源字段→标准字段→Property→指标/规则→报告影响链 |
| 数据资产目录 | 资产发现、所有者、敏感级别、用途和授权 |
| 数据服务 | API/SQL/对象服务等受控数据服务 |
| 时态数据 | 生效时间、失效时间、记录时间及历史切片 |

实体身份解析属于 MDM/数据治理。Ontology 消费已经治理的稳定标识，并通过 Primary Key 形成 Object 身份；低置信度模糊匹配必须人工确认，不应由 Ontology 自动“合并对象”。

### 3.7 数据接入与源系统层

#### 3.7.1 接入方式

- ETL/ELT：适用于批量历史与 T+1 数据；
- CDC：适用于需要低延迟增量的数据域；
- API：适用于标准服务化系统；
- 文件交换：适用于暂不具备在线接口的系统；
- 文档解析/OCR：仅用于形成可追溯文档事实，原文件必须保留。

所有源系统连接应使用只读账号/只读接口，限制 SQL 权限、API 方法和网络访问范围。

#### 3.7.2 内部业务系统

| 数据源 | 优先级 | 关键数据 |
| --- | --- | --- |
| ERP/财务 | P0 | 凭证、科目、客户/供应商、采购订单、应收应付 |
| 司库/银行 | P0 | 账户、流水、余额、融资、担保 |
| 合同/发票 | P0 | 合同要素、履约、发票、付款条件 |
| 产权/工商内部库 | P0 | 股权、股东、企业层级、变更 |
| HR | P1 | 组织、岗位、人员、任免、授权 |
| 采购/招投标 | P1 | 采购计划、投标、评标、中标、供应商 |
| 投资/项目/资产 | P1/P2 | 立项、尽调、进度、成本、资产处置 |
| OA/三重一大 | P1 | 事项、会议、审批、授权、决策记录 |
| 审计/历史案例 | P1 | 问题、底稿、整改、已知风险样本 |

#### 3.7.3 外部数据源

工商、司法、信用、招投标、银行、税务、舆情等外部数据必须记录来源、授权方式、获取时间、许可范围和更新频率。外部数据用于补充事实和风险信号，不能因来源不明直接形成违规结论。

### 3.8 基础设施层

| 组件 | 要求 |
| --- | --- |
| 部署 | 私有化或混合云，按客户安全域部署 |
| 容器平台 | Kubernetes/容器编排、弹性扩缩、灰度发布 |
| 微服务 | 服务治理、注册发现、限流、熔断、配置管理 |
| 计算 | 通用计算、OLAP、图计算、AI 推理资源分池 |
| 存储 | 结构化、对象存储、搜索索引、备份分层 |
| 消息/缓存 | 事件流、任务队列、分布式缓存 |
| 网络 | 安全域隔离、东西向/南北向访问控制 |
| 容灾 | 备份恢复、RPO/RTO、跨机房/跨域方案 |
| 可观测性 | Metrics、Logs、Traces、作业与数据链路监控 |
| 信创 | 建立 CPU/OS/数据库/中间件/AI 模型兼容矩阵，不在架构层绑定单一厂商 |

### 3.9 运维、安全与合规治理

#### 3.9.1 运维保障

统一监控服务可用性、接口、数据接入、索引、规则执行、模型调用和任务队列；关键链路建立 Runbook、容量基线、告警分级、降级路径和恢复演练。

#### 3.9.2 安全保障

- SSO/MFA 与统一身份；
- RBAC + 数据域/组织域/敏感级别的细粒度授权；
- Ontology 模型元数据权限与 Object 数据权限分离；
- 传输/存储加密，敏感字段脱敏；
- 查询、导出、权限、模型、规则、本体变更全部审计；
- 专案数据独立授权，系统管理员默认无业务数据全量权限。

#### 3.9.3 合规与模型治理

- 数据最小化、用途限定、授权期限和导出控制；
- 规则必须绑定制度依据并版本化；
- 模型必须有评测集、版本、输入输出约束和人工复核门禁；
- 审计日志采用追加写/防篡改存储，保留周期按客户法规和制度确定；
- 任何监管结论必须区分：异常、线索、疑点、核实事实、正式结论。

## 4. 端到端业务流程

### 4.1 流程一：合同付款穿透

| 步骤 | 动作 | 涉及层 |
| --- | --- | --- |
| 1 | 只读接入合同、发票、验收、付款、账户和审批记录 | 数据接入 |
| 2 | 通过 MDM 对齐合同方、供应商、账户和企业主标识 | 数据治理 |
| 3 | 映射为 Contract、Payment、BankAccount、Enterprise 等 Objects，并建立 Link Types | Ontology |
| 4 | 形成目标 Object Set，沿 Link 执行 Search Around；复杂关系交给图分析 | Ontology/图分析 |
| 5 | 规则检查付款对象一致性、比例、时序、贸易背景和审批约束 | 规则引擎 |
| 6 | 命中后生成线索，包含路径、时间线、规则版本、证据和缺失数据 | 风险分析 |
| 7 | 人工核查、补充材料、确认或驳回 | 监管协同 |
| 8 | 对确认问题生成整改跟踪/专项移交/处置建议，并回收规则与模型反馈 | 监管协同 |

整个链路不修改源业务系统。若监管人员决定暂停付款或调整业务流程，由原业务系统按照既有授权机制执行，DRP 只记录依据和后续结果。

### 4.2 流程二：股权与实际控制穿透

工商/产权数据只读接入 → MDM 统一 Enterprise/Person 身份 → Ontology 建立 owns/controlled by 等 Link → 按指定日期形成对象集 → Search Around 获取一跳关系 → 图分析执行多层控制权累积/环路检测 → 输出实际控制链、最终受益关系和证据来源。

### 4.3 流程三：关联交易识别

交易对手 Object Set → Search Around 到股东/实控人/高管 → 图分析扩展人员和企业关系 → 与员工/董监高及申报关系比较 → 规则命中 → 形成待核查线索。

### 4.4 流程四：线索闭环

```text
新建 → 初审 → 补充材料 → 复核 → 确认 / 驳回
                         ↓
               整改跟踪 / 专项移交 / 报告
                         ↓
                   复核销号 → 关闭
```

误报、漏报和人工改判必须进入评测集，用于规则、模型、映射或数据质量的后续优化。

### 4.5 流程五：Ontology 挖掘与发布

G0 资产登记 → G1 证据提取 → G2 语义净化 → G3 Object/Property/Link/Interface 候选建模 → G4 评审包 → G5/C0 专家裁决 → C1 数据契约与映射 → C2 权限/影响评审 → C3 发布 → 对象索引 → 历史回放/影子验证 → 正式只读查询。

### 4.6 流程六：风险升级与责任事实链

高风险线索确认 → 汇总制度条款、对象关系、决策记录、合同/项目/付款证据 → 形成责任相关事实链 → 有权人员复核 → 形成整改要求、专项移交或业务处置建议 → 跟踪外部执行结果 → 复核销号。

DRP 不直接执行“冻结、挂起、终止”等源业务动作；它负责把事实和证据组织到足以支持授权人员决策的程度。

## 5. 数据与 Ontology 字典（试点范围）

### 5.1 核心 Object Types 与 Properties

| Object Type | 关键 Properties | 权威来源 | Primary Key 建议 |
| --- | --- | --- | --- |
| Enterprise | 名称、曾用名、注册地、状态、企业层级 | 工商/产权/主数据 | 统一社会信用代码 |
| Person | 姓名、任职、人员状态；敏感标识加密/哈希 | HR/登记 | 客户内部人员主键或受保护的稳定标识 |
| OrgUnit | 编码、名称、层级、类型 | HR/组织主数据 | 组织编码 |
| BankAccount | 账号脱敏、开户行、户名、币种、状态 | 司库/银行 | 受保护账号标识+开户行 |
| Project | 名称、类型、预算、状态、起止时间 | 投资/项目 | 项目编码 |
| Contract | 合同号、金额、币种、日期、状态、条款摘要 | 合同系统 | 合同主键/合同编号 |
| Invoice | 发票号、金额、税额、购销方、日期 | 发票系统 | 发票唯一标识 |
| Payment | 付款编号、金额、时间、用途、状态 | 财务/司库 | 付款单主键 |
| Meeting/ApprovalEvent | 事项、时间、参与人、审批意见、结果 | OA/三重一大 | 事件主键 |
| RiskClue | 摘要、等级、状态、规则版本、证据 | DRP | 线索编号 |
| EvidencePackage | 来源、时间、哈希、访问权限 | DRP | 证据包编号 |
| RemediationTask | 责任主体、期限、状态、结果 | DRP | 任务编号 |

说明：`Shareholder`、`ActualController`、`UltimateBeneficiary` 不必机械建成 Object Type。若其本质是 Enterprise/Person 的角色或关系，应优先通过 Object + Link 表达；只有当其具有独立身份、生命周期和业务记录时才建成单独 Object Type。

### 5.2 核心 Link Types 与时间语义

| Link 语义 | 两端 | 关系数据应可追溯的信息 | 时间要求 |
| --- | --- | --- | --- |
| owns / owned by | Enterprise/Person ↔ Enterprise | 持股比例、出资额、来源 | 持有区间 |
| controls / controlled by | Enterprise/Person ↔ Enterprise | 控制方式、依据 | 控制区间 |
| employed by / employs | Person ↔ Enterprise/OrgUnit | 岗位、任职依据 | 任职区间 |
| party to | Enterprise ↔ Contract | 甲乙方角色 | 合同有效期 |
| related to project | Contract/Payment ↔ Project | 关系类型 | 业务有效期 |
| based on | Payment ↔ Contract/Invoice/Acceptance | 金额对应、单据号 | 单据时点 |
| paid through | Payment ↔ BankAccount | 付款/收款方向 | 交易时点 |
| account belongs to | BankAccount ↔ Enterprise | 控制依据 | 账户有效期 |
| approved by | ApprovalEvent ↔ Person/OrgUnit | 审批角色 | 审批时点 |
| evidence for | EvidencePackage ↔ RiskClue/Case | 证据类型、哈希 | 证据版本时间 |

关系数据必须能够追溯到来源、有效时间/记录时间、证据和数据版本。若这些信息需要成为一等查询对象，例如“某次持股关系”的持股比例、出资额、起止时间和依据，应建模为 `EquityHolding` 等关系 Object，再通过 Links 连接 Holder 与 Enterprise。置信度仅用于推断关系；来自权威系统的确定性事实不应被统一包装成概率。

### 5.3 Shared Properties 与 Interfaces

优先抽取跨对象的一致属性元数据，例如 `status`、`effectiveFrom`、`effectiveTo`、`sourceSystem`、`lastUpdatedAt`，但 Shared Property 共享的是 Property 定义和元数据，不意味着底层对象共用同一份数据。

Interfaces 用于表达多个 Object Type 共同满足的业务契约，例如“可监管主体”“具有金额的交易事件”等；接口应服务于统一查询和应用开发，不用于模拟业务继承树。

### 5.4 Object Sets 与监管对象集合

建议把常用监管范围沉淀为可复用 Object Set 定义，例如：

- 三级以下企业集合；
- 近 12 个月大额合同集合；
- 高风险供应商集合；
- 付款比例异常的 Payment 集合；
- 逾期未整改的 RiskClue/RemediationTask 集合。

规则、应用和 AI 应尽量复用同一对象集定义，避免各自编写不同 SQL 导致口径漂移。

### 5.5 指标示例

| 指标 | 口径 | 计算基础 |
| --- | --- | --- |
| 预付款比例 | 预付款金额 / 合同金额 | Contract + Payment Object Set |
| 资金集中率 | 归集资金 / 可归集资金 | 司库数据 |
| 银企直连率 | 直连账户 / 全部账户 | BankAccount |
| 合同数据完整率 | 完整合同 / 全部合同 | 数据质量 |
| 线索证据完整率 | 证据完整线索 / 全部线索 | RiskClue + EvidencePackage |
| 整改按期完成率 | 按期销号 / 到期任务 | RemediationTask |
| 关系时间完整率 | 带有效时间的核心 Links / 全部核心 Links | Ontology/数据质量 |

指标定义、口径、来源、时间粒度、聚合方式和版本独立管理。规则引用指标定义，不把计算逻辑散落在每条规则中。

## 7. 权限、安全与版本治理

### 7.1 权限分层

权限至少分为四个维度：

1. **功能权限**：能否访问驾驶舱、规则中心、本体管理、线索工作台；
2. **Ontology Resource 权限**：能否查看/编辑 Object Type、Link Type、Interface、Mapping 等模型元数据；
3. **Object 数据权限**：能否读取某组织、某业务域、某敏感级别的对象实例；
4. **操作与导出权限**：能否创建 DRP 内部线索/任务、审批模型发布、导出敏感数据。

模型编辑权限不自动授予业务数据读取权限；系统管理员也不自动拥有高敏感数据权限。

### 7.2 角色 × 数据域矩阵（示例）

| 角色 | 组织/业务数据 | 敏感自然人 | 线索/协同 | 规则 | Ontology 元数据 | 证据包 |
| --- | --- | --- | --- | --- | --- | --- |
| 监管人员 | 读（授权范围） | 读（授权） | 处理 | 读 | 读 | 读 |
| 审计/纪检 | 读（专项范围） | 专项授权 | 复核/专项 | 读 | 读 | 专项 |
| 企业用户 | 读（本企业） | 最小必要 | 反馈/整改 | 禁 | 禁 | 按任务 |
| 数据管理员 | 治理范围内读 | 禁/脱敏 | 禁 | 禁 | 读 | 禁 |
| 本体工程师 | 仅调试所需脱敏样本 | 禁 | 禁 | 读 | 编辑/发布按权限 | 禁 |
| 规则工程师 | 评测所需数据 | 脱敏 | 读 | 编辑/发布按权限 | 读 | 只读 |
| 系统管理员 | 元数据/运行信息 | 禁 | 禁 | 禁 | 非默认编辑 | 禁 |

源系统连接账户在所有情况下均应为只读。

### 7.3 数据分级

| 级别 | 示例 | 授权原则 |
| --- | --- | --- |
| L1 公开 | 企业名称、公开工商信息 | 按公开范围 |
| L2 内部 | 财务汇总、业务流程数据 | 按组织/岗位 |
| L3 敏感 | 账户、交易明细、薪酬 | 最小必要、审批、导出控制 |
| L4 高度敏感 | 身份标识、纪检专案 | 专案授权、期限控制、全程审计 |

### 7.4 版本与发布

统一管理：

- Ontology schema 版本；
- Backing Datasource / Property Mapping / Index 配置版本；
- 规则版本；
- 模型与提示模板版本；
- 指标版本；
- 数据契约与标准版本。

发布前执行兼容性检查、影响分析和历史回放。Primary Key、Link 端点、Property 类型等破坏性变化必须走专项评审，并保留明确回滚点。

### 7.5 审计留痕

必须记录：谁、何时、访问了什么对象/数据域、执行了什么查询、导出了什么、修改了哪些 DRP 配置、审批人是谁、使用了哪个模型/规则/本体版本。日志采用追加写和防篡改机制，保留周期按客户制度及法规要求确定。

### 8.3 运行成熟度分级（全程只读源系统）

| 数据 | 数据质量阻断项关闭率 | 已关闭 P0 数据问题 / 全部 P0 问题 | 100% 上线前关闭 |
| Ontology | Mapping 可追溯率 | Property/Link 可追溯到 Backing Datasource 比例 | 100% |
| Ontology | 核心对象查询成功率 | 评测查询正确返回 / 全部评测查询 | ≥ 99% |
| 性能 | 常用对象穿透 P95 | Object Search/Search Around/常用组合查询 | 试点目标 < 5 秒 |
| 规则 | 已发布规则条款可追溯率 | 绑定正式制度依据的规则 / 已发布规则 | 100% |
| 效果 | 历史已知问题召回率 | 命中历史问题 / 全部历史问题 | ≥ 80% |
| 效果 | 高风险线索有效率 | 人工确认有效 / 高风险线索 | 建立基线并持续提升 |
| 效果 | 误报率 | 人工驳回 / 全部线索 | 建立基线并持续下降 |
| 效率 | 单条线索调查耗时下降 | 试点 vs 人工基线 | ≥ 30% |
| 闭环 | 整改按期完成率 | 按期销号 / 到期任务 | ≥ 90% |
| 治理 | 破坏性 Ontology 变更未评审数 | 未经评审上线次数 | 0 |

数值目标应在试点基线建立后由客户确认，不应在数据质量和场景复杂度未知时承诺统一固定值。

### 9.2 评测集

评测集至少覆盖：

- Object/Property Mapping 正确性；
- Primary Key 唯一性与身份对齐；
- Link 正确性与时间切片；
- Object Search、Filter、Aggregation、Search Around；
- 规则正例、反例、边界值和排除条件；
- 图算法已知关系样本；
- AI 问答的事实引用、拒答和权限边界；
- 历史审计/监管案例回放。

每条样本保存输入、预期结果、依据、数据版本和执行版本，以支持回归。

### 9.3 试点成功标准

核心成功标准不是“建了多少 Object Type”或“图里有多少边”，而是：

> **一条过去需要多人跨系统数天调查的问题，能否在一个监管工作台内完成对象定位、关系穿透、时间还原、规则解释、原始证据核对、人工复核和闭环跟踪，并且全过程可审计、可重现。**

### 10.2 架构红线

1. **“Ontology = DRP 全平台”**：不成立；Ontology 只负责统一业务语义与对象查询表示；
2. **“DRP 只读 = 不需要对象索引”**：不成立；只读限制的是源系统写回，高性能对象查询仍可使用派生索引；
3. **“图数据库 = Ontology”**：不成立；图存储是实现选择，Ontology 是语义模型；
4. **“AI 自动穿透并定性”**：不成立；AI 不能替代规则、事实查询和有权人员判断；
5. **“MDM 由 Ontology 自动解决”**：不成立；实体身份归一属于数据治理；
6. **“监管规则是 Ontology primitive”**：不成立；规则属于分析智能层；
7. **“Object Type Group 是继承层级”**：不成立；它是分类/发现机制；
8. **“一套模型适用所有集团”**：不成立；核心对象可复用，行业和企业扩展必须治理。

### 10.3 技术降级策略

| 难点 | 降级方案 |
| --- | --- |
| 身份解析 | 先采用强主键；模糊匹配进入人工确认队列 |
| 时间关系 | 先支持当前态 + 指定日期切片，再扩展完整双时态 |
| 对象索引 | 先覆盖 P0 Object Types 和常用查询字段 |
| Search Around 性能 | 限制默认深度；复杂多跳转图计算服务 |
| 规则自动生成 | 先人工结构化录入，AI 仅生成候选 |
| 数据缺失 | 明确展示缺失字段，不强行形成结论 |
| 实时性 | 先 T+1/小时级，再对高价值场景升级 CDC |
| 模型能力 | 确定性规则兜底，AI 可替换、可关闭 |

## 结论

本方案最终形成的是一套以**只读数据接入 + 数据治理 + Ontology 统一语义 + 分层智能分析 + 监管协同**为核心的穿透式监管体系。

其技术关系可以概括为：

```text
源业务系统（权威事实）
        ↓ READ ONLY
数据平台与治理（可信数据）
        ↓
Ontology（Object / Property / Link / Object Set）
        ↓
规则 / 风险模型 / 图分析 / 检索 / OLAP / AI
        ↓
风险分析与监管协同（线索 / 证据 / 核查 / 整改跟踪）
        ↓
监管应用（穿透 / 驾驶舱 / AI监管 / 报告）
```

最关键的架构原则有五点：

1. 源系统只读，DRP 不成为第二套业务主系统；
2. Ontology 负责业务语义与对象查询，不吞并 MDM、规则、图算法和工作流；
3. 上层优先面向 Object、Object Set 和 Link，而不是底层表；
4. AI 只能基于受控事实和工具辅助分析，正式结论必须人工复核；
5. 验收以可穿透、可解释、可追溯、可复核、可治理为标准，而不是以对象数量、图规模或模型数量为标准。

因此，试点建设应优先打通“一条真实监管问题从数据到对象、从对象到关系、从关系到规则、从规则到线索、从线索到证据和闭环”的完整链路，再在同一 Ontology 与治理框架下逐步扩展业务域。
