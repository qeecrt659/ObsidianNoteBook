# 国资 DRP 技术架构详细说明

> **文档定位**：本文件是《国资DRP技术架构》总体架构图的详细架构说明，可用于总体方案设计、架构评审、模块拆分、详细设计和后续研发任务分解。  
> **核心架构思想**：**数据平台 + Ontology 语义中枢 + 规则/风险模型/图分析 + AI Agent + 风险闭环 + 监管应用**。  
> **说明**：本文的层级与模块名称严格沿用当前《国资DRP技术架构》；其中模块职责、输入输出、技术边界、接口设计和实现建议，是在现有架构基础上的进一步架构设计扩展。

---

# 1. 建设目标与架构定位

## 1.1 DRP 的技术定位

国资 DRP 不应被建设成单一的“监管大屏”“风险预警系统”“知识图谱系统”或“AI 问答系统”，而应当被定位为：

> **面向国资监管的数字监管平台（Digital Regulatory Platform），以统一数据底座承载事实数据，以 Ontology 建立业务语义和关系模型，以规则、图分析、风险模型和 AI 构建智能监管能力，以监管工作流形成风险处置闭环。**

平台最终需要同时解决五类问题：

1. **数据在哪里**：跨 ERP、财务、司库、采购、合同、项目、投资、资产、三重一大、人力以及外部工商、司法、信用等系统统一获取监管所需数据。
2. **数据代表什么**：通过 Ontology 将表、字段、编码转化为 Enterprise、Person、Contract、Payment、Supplier、Project、Investment、Decision、Risk 等业务对象。
3. **对象之间有什么关系**：构建股权、控制、任职、合同、采购、付款、项目、审批、账户、交易对手等可计算关系。
4. **哪些现象属于风险**：通过指标、规则、图算法、机器学习模型和 AI 识别异常。
5. **发现后如何处理**：通过线索、核查、说明、证据、整改、复核、销号和责任追溯形成完整监管闭环。

# 2. 关键架构原则

## 2.1 数据平台与 Ontology 分层

**数据平台解决“事实数据的存储与计算”，Ontology 解决“事实数据的业务语义”。**

例如：

```text
底层表：
T_CORP
T_CONTRACT
T_PAYMENT
T_SUPPLIER

        ↓ Semantic Mapping

Ontology：
Enterprise
Contract
Payment
Supplier
```

不能把 Ontology 设计成新的数据仓库，也不能要求所有原始数据都复制到 Ontology Runtime。

---

## 2.2 Ontology 不等于知识图谱

知识图谱偏重：

- 节点；
- 边；
- 图遍历；
- 图算法；
- 关系发现。

而 DRP Ontology 需要覆盖：

```text
Object
Property
Link
Event
Metric
Rule
Action
Policy
Version
Permission
State
Timeline
Semantic API
```

因此，图数据库只是 Ontology Runtime 可以使用的一种底层关系计算技术。

---

## 2.3 应用不直接依赖底层数据库

推荐：

```text
监管应用
   ↓
Ontology API / Query API / Graph API
   ↓
Ontology Runtime
   ↓
数据服务 / 查询引擎
   ↓
底层数据平台
```

不推荐：

```text
监管应用 A → 直接查 ERP 表
监管应用 B → 直接查司库表
监管应用 C → 直接查合同表
AI Agent    → 任意生成 SQL
```

后者会导致应用与数据源强耦合，后续数据结构一变，大量应用同时修改。

---

## 2.4 风险识别与风险处置解耦

风险模型负责：

```text
识别风险
```

风险闭环负责：

```text
处理风险
```

风险识别输出统一的 `RiskEvent`，再由监管工作流决定后续核查、整改和销号逻辑。

---

## 2.5 确定性规则优先，AI 做增强

监管判断中能够被明确制度、阈值、公式表达的逻辑，应优先由规则引擎执行。

例如：

```text
累计付款 > 合同金额
```

不应首先交给大模型判断。

AI 更适合：

- 非结构化文本理解；
- 合同条款抽取；
- 风险解释；
- 多源信息归纳；
- 自然语言查询；
- 调用规则和分析工具；
- 自动形成报告。

# 3. 第一层：用户与入口层

## 3.1 层级职责

用户与入口层是所有监管能力的统一入口，主要解决“谁访问、从哪里访问、看到什么、需要处理什么”的问题。

这一层原则上应当保持轻量，不承载复杂监管业务逻辑。复杂业务应下沉到应用服务、Ontology、规则和工作流层。

---

## 3.2 监管人员

### 职责

监管人员是平台最核心的业务用户，主要完成：

- 查看集团或企业风险态势；
- 进入具体企业、项目、合同、付款等对象进行穿透；
- 查看风险预警；
- 发起风险核查；
- 审核企业说明；
- 查看证据材料；
- 下发整改任务；
- 复核整改结果；
- 销号；
- 责任追溯。

### 数据范围

应通过组织、企业层级、监管范围、事项类型等维度控制可访问对象。

### 最佳实践

不要仅使用传统 RBAC 角色权限。监管人员往往需要：

```text
角色权限
+
组织数据权限
+
对象实例权限
+
字段权限
+
关系穿透权限
+
Action 执行权限
```

---

## 3.3 企业用户

### 主要职责

企业用户主要负责监管协同：

- 数据报送；
- 风险事项接收；
- 企业说明；
- 证据上传；
- 整改反馈；
- 补充材料；
- 对监管任务进行状态反馈。

### 架构边界

企业用户不应直接访问所有监管模型结果。

例如：

- 内部模型评分；
- 尚未正式形成线索的模型候选；
- 其他企业敏感数据；
- 内部审计分析逻辑。

应通过“监管可见”和“企业可见”双重可见性控制。

---

## 3.4 领导决策用户

主要关注：

- 集团总体态势；
- 高风险企业；
- 重点风险领域；
- 风险趋势；
- 重大事项；
- 重点项目；
- 风险处置进度；
- 整改完成率；
- 同行业/同类型企业对标。

领导用户的页面设计应强调“概要 → 原因 → 穿透”，不能只展示指标。

例如：

```text
风险企业：27 家
      ↓
资金类风险：12 家
      ↓
XX 公司：高风险
      ↓
异常付款 3 笔
      ↓
合同 / 项目 / 供应商 / 审批人
```

---

## 3.5 外部监管 / 审计用户

主要适用于：

- 联合监管；
- 专项检查；
- 外部审计；
- 巡视巡察；
- 纪检监督；
- 临时授权检查。

此类用户应采用：

- 临时授权；
- 最小权限；
- 访问期限；
- 全程审计；
- 高敏数据水印；
- 下载审批；
- 导出控制。

---

## 3.6 系统管理员

系统管理员负责：

- 用户管理；
- 组织管理；
- 权限管理；
- 系统配置；
- 字典配置；
- 接入配置；
- 运行状态查看。

需要避免系统管理员天然拥有业务数据读取权限。

推荐区分：

```text
平台管理员
安全管理员
审计管理员
业务管理员
```

形成职责分离。

# 4. 统一门户 Portal

## 4.1 单点登录

统一身份认证入口，支持：

- 企业统一身份平台；
- LDAP / AD；
- OAuth2 / OIDC；
- SAML；
- 国密认证体系；
- MFA 多因素认证。

登录成功后应统一生成平台用户上下文，包括：

```text
User
Organization
Role
DataScope
ObjectPermission
ActionPermission
SecurityLevel
```

---

## 4.2 消息中心

统一接收：

- 风险预警；
- 监管通知；
- 核查通知；
- 整改通知；
- 报送提醒；
- 工作流提醒；
- 系统通知。

消息中心只负责消息聚合，不应自己实现业务状态。

---

## 4.3 工作台

工作台根据用户身份动态展示：

- 待处理风险；
- 待审批事项；
- 待报送任务；
- 关注企业；
- 重点项目；
- 常用监管应用；
- 最近访问对象；
- 个性化指标。

---

## 4.4 待办中心

所有业务系统的工作任务统一转成 Task。

推荐统一任务模型：

```yaml
Task:
  taskId:
  taskType:
  sourceType:
  sourceObjectId:
  assignee:
  organization:
  priority:
  status:
  dueDate:
  createdAt:
```

避免每个应用单独开发一套待办系统。

---

## 4.5 多端适配

支持：

- PC；
- 移动端；
- 监管大屏。

不同终端需要控制可操作能力。

例如移动端适合：

- 查看；
- 审批；
- 消息；
- 简单处置。

复杂图谱穿透和模型分析更适合 PC。

---

## 4.6 个性化配置

包括：

- 首页布局；
- 常用菜单；
- 关注企业；
- 常用指标；
- 风险订阅；
- 消息订阅。

个性化配置只能影响展示，不应改变统一监管口径。

# 5. 第二层：监管应用层

# 5.1 监管驾驶舱

监管驾驶舱用于管理层快速识别“哪里有问题”，然后能够继续穿透到具体业务事实。

---

## 5.1.1 集团态势总览

### 目标

从集团整体维度展示：

- 企业数量；
- 企业层级；
- 股权结构；
- 资产规模；
- 营收；
- 利润；
- 负债；
- 投资；
- 项目；
- 合同；
- 资金；
- 风险事件。

### 输入

- Ontology Enterprise；
- Metric；
- RiskEvent；
- Financial Metric；
- Project / Investment / Contract 等对象。

### 输出

形成集团级监管视图。

### 关键原则

所有数字必须能继续追溯到底层对象，而不是孤立 KPI。

---

## 5.1.2 风险态势大屏

展示：

- 风险总量；
- 风险等级；
- 风险领域；
- 风险企业分布；
- 新增风险；
- 已处理风险；
- 长期未处理风险；
- 风险趋势；
- 高风险对象。

推荐每个指标都可以：

```text
集团风险
→ 企业风险
→ 风险事件
→ 触发规则
→ 业务对象
→ 原始事实
```

---

## 5.1.3 穿透分析总览

提供统一穿透入口。

推荐支持：

- 从企业开始；
- 从风险开始；
- 从项目开始；
- 从合同开始；
- 从交易开始；
- 从人员开始；
- 从供应商开始。

穿透不是简单树形钻取，而是围绕 Ontology Link 动态展开。

---

## 5.1.4 指标趋势分析

指标应由统一 Metric 定义。

至少需要：

- 指标口径；
- 计算公式；
- 数据来源；
- 统计周期；
- 适用对象；
- 版本；
- 负责人。

避免各应用重新计算同名指标。

---

# 5.2 穿透式监管应用

## 5.2.1 组织股权穿透

### 监管目标

回答：

- 集团到底控制多少企业；
- 企业层级多深；
- 哪些是控股企业；
- 哪些是参股企业；
- 哪些存在交叉持股；
- 谁是最终控制人；
- 谁是最终受益人；
- 是否存在控股不控权；
- 董事、高管、法人和股权控制是否一致。

### 核心 Ontology

```text
Enterprise
Person
Shareholder
Equity
Board
Executive
BeneficialOwner
ControlRelation
```

### 典型 Link

```text
Enterprise ─owns→ Enterprise
Person ─owns→ Enterprise
Person ─directorOf→ Enterprise
Enterprise ─controls→ Enterprise
Enterprise ─investsIn→ Enterprise
```

### 关键算法

- 多级股权路径；
- 最终受益人；
- 实际控制人；
- 循环持股；
- 一致行动关系；
- 控制链；
- 持股比例累计。

### 输出

- 股权穿透树；
- 控制关系图；
- 企业层级图；
- 风险控制链；
- 异常企业清单。

---

## 5.2.2 资金穿透监管

### 监管目标

对一笔资金回答：

```text
谁付的钱？
为什么付？
从哪个账户付？
付给谁？
对应哪个合同？
对应哪个项目？
是否经过审批？
供应商是谁？
最终收款主体是谁？
是否存在关联方？
```

### 核心对象

```text
Payment
Collection
BankAccount
Enterprise
Contract
Supplier
Project
Invoice
Approval
```

### 关键分析

- 大额支付；
- 无合同付款；
- 超合同付款；
- 异常收款账户；
- 多账户分拆支付；
- 循环资金；
- 资金回流；
- 关联主体收款；
- 项目进度和付款比例异常。

### 技术要点

资金数据量通常较大，不能把所有流水都强制存入图数据库。

推荐：

```text
交易事实 → 关系型 / OLAP 数据库
高价值关系 → 图计算索引
业务语义 → Ontology
```

## 5.2.4 合同穿透监管

### 核心链路

```text
预算
→ 项目
→ 采购
→ 合同
→ 补充协议
→ 发票
→ 验收
→ 付款
```

### 重点风险

- 合同倒签；
- 超合同付款；
- 无合同付款；
- 补充协议异常；
- 长期未履约；
- 付款条件未满足；
- 合同金额异常；
- 关联交易。

### 合同 AI

合同文本属于非结构化数据，可以使用大模型完成：

- 条款抽取；
- 风险条款识别；
- 付款条件抽取；
- 违约条款识别；
- 合同主体识别。

抽取结果应回写为结构化对象属性或 Event，而不是只保留在模型回答里。

## 5.2.5 投资穿透监管

### 核心对象


## 5.2.6 三重一大穿透

### 监管目标

不只判断“是否开会”，而是穿透：

```text
事项
→ 决策依据
→ 提案人
→ 参会人
→ 表决
→ 决策结果
→ 审批权限
→ 执行
→ 合同 / 项目 / 资金
→ 最终结果
```

### 重点风险

- 未经决策；
- 决策程序不完整；
- 越权决策；
- 重大事项拆分；
- 决策后长期未执行；
- 决策结果与资金执行不一致。

---

## 5.2.7 供应商 / 客户穿透

### 核心分析

围绕 Supplier / Customer 穿透：

```text
主体
→ 股东
→ 实控人
→ 董监高
→ 关联企业
→ 历史投标
→ 历史合同
→ 历史付款
→ 司法
→ 信用
```

### 典型风险

- 内部人员关联；
- 供应商集中度过高；
- 新成立供应商获得大额合同；
- 频繁关联交易；
- 高风险司法主体；
- 多供应商实际由同一主体控制。

---

```text
→ 决策
→ 招采
→ 合同
→ 付款
→ 进度
→ 验收
→ 决算
```

### 重点分析

- 项目进度；
- 投资进度；
- 付款进度；
- 合同执行；
- 项目超概算；
- 项目延期；
- 验收异常；
- 资金和进度不匹配。

# 7. 第四层：AI / 规则 / 分析智能层

# 7.1 规则引擎

## 7.1.1 规则配置

规则应尽量使用 Ontology 对象和属性表达。

例如：

```text
SUM(Payment.amount WHERE Payment.forContract = Contract)
>
Contract.amount
```

而不是：

```sql
SELECT ... FROM T_PAYMENT JOIN T_CONTRACT ...
```

这样业务规则不依赖物理表结构。

# 8. 第五层：Ontology 语义中枢层（核心）

# 8.1 Ontology Management

## 8.1.1 Object Type

Object Type 是现实世界业务对象的类型定义。

例如：

```text
Enterprise
Person
Contract
Payment
Supplier
Project
Investment
Decision
RiskEvent
```

每个 Object Type 至少定义：

```yaml
ObjectType:
  id:
  name:
  displayName:
  primaryKey:
  properties:
  links:
  events:
  actions:
  permissions:
  version:
```

---

## 8.1.2 Property

Property 是对象的属性。

例如：

```text
Contract.amount
Contract.signDate
Contract.status
```

需要定义：

- 数据类型；
- 是否必填；
- 枚举；
- 单位；
- 格式；
- 脱敏策略；
- 来源；
- 可搜索性；
- 是否作为指标维度。

---

## 8.1.3 Link Type

Link Type 是穿透监管的核心。

定义：

- 起点类型；
- 终点类型；
- 方向；
- 基数；
- 语义；
- 时间有效性；
- 来源；
- 权限。

例如：

```text
Contract ─supplier→ Supplier
Payment ─forContract→ Contract
Person ─directorOf→ Enterprise
```

---

## 8.1.4 Event

Event 用于描述发生过的事实。

例如：

```text
ContractSigned
PaymentExecuted
ProjectApproved
RiskDetected
RectificationCompleted
```

事件需要：

- 时间；
- 发起主体；
- 关联对象；
- 前状态；
- 后状态；
- 事件数据。

---

## 8.1.5 Metric

Metric 是统一业务指标语义。

例如：

```text
DebtRatio
PaymentRatio
InvestmentReturn
SupplierConcentration
```

---

## 8.1.6 Rule

Rule 表示监管判断逻辑。

规则应引用 Ontology Object / Property / Metric，而不是直接绑定表字段。

---

## 8.1.7 Action

Action 是可对对象执行的业务动作。

例如：

```text
CreateInvestigation
RequestExplanation
RequestEvidence
CreateRectification
EscalateRisk
CloseRisk
```

Action 需要校验：

- 当前对象状态；
- 当前用户权限；
- 前置条件；
- 执行结果；
- 审计。

---

## 8.1.8 Policy

Policy 表示制度、政策、授权和约束。

用于将规则与监管依据连接。

例如：

```text
Rule
 ↓ basedOn
Policy
```

便于解释“为什么这个行为被判定为风险”。

---

## 8.1.9 模型版本管理

任何 Ontology 变更都需要版本化：

- 新增对象；
- 删除对象；
- Property 修改；
- Link 修改；
- 规则修改；
- Action 修改。

版本需要支持：

```text
Draft
→ Review
→ Approved
→ Published
→ Deprecated
```

---

## 8.1.10 模型发布与审批

生产 Ontology 不应由开发人员直接修改。

推荐：

```text
设计
→ 校验
→ 影响分析
→ 测试
→ 审批
→ 发布
→ 监控
→ 回滚
```

---

# 8.2 三层 Ontology 模型

## 8.2.1 标准本体

由监管平台定义跨企业通用语义：

```text
Enterprise
Person
Contract
Payment
Supplier
Project
Investment
Risk
```

# 8.3 Ontology Runtime

## 8.3.1 业务对象实例化

底层数据经过语义映射形成实例：

```text

```

实例本身可以采用：

- 虚拟化；
- 混合模式。

海量明细对象建议优先使用虚拟化/按需查询，不必全部复制。

## 8.3.2 关系实例化

关系来源：

- 原始业务主外键；
- 主数据映射；
- 规则推导；
- 图算法推导；
- 外部数据；
- 人工确认。

需要区分：

```text

```

语义映射连接：

```text

      ↕
Ontology Schema
```

需支持：

- 表 → Object；
- 字段 → Property；
- Join → Link；
- 事件流 → Event；
- SQL / API → DataSource。

---

## 8.3.4 语义查询

上层查询业务语义：

```text

```

Ontology Runtime 将其转换为具体数据查询计划。

---

## 8.3.5 语义权限

权限粒度可达到：

```text

Object Instance
Property
Link
Action
```

例如：

```text

但不能看 Executive.salary
可以从 Enterprise 穿透到 Contract
但不能穿透到某些 BankAccount
```

---

## 8.3.6 语义视图

根据业务场景对相同 Ontology 创建不同视图。

例如：

```text

采购监管视图
领导驾驶舱视图
```

视图不是复制数据，而是定义可见对象和关系。

---

## 8.3.7 对象时间线

保存对象重要事件：

```text

├─ Created
├─ Approved
├─ Signed
├─ Changed
├─ Paid
└─ Closed
```

时间线对于调查和责任追溯非常重要。

---

## 8.3.8 事件与状态管理

对象需要状态机。

例如：

```text

Detected
→ Confirmed
→ Investigating
→ Rectifying
→ Reviewing
→ Closed
```

Action 根据状态决定能否执行。

# 15. 典型端到端案例：异常付款穿透

假设系统发现：

```text
Payment #P001
金额：5000 万
```

第一步：识别付款主体：

```text
Payment
→ BankAccount
→ Enterprise
→ Parent Enterprise
→ Group
```

第二步：识别业务原因：

```text
Payment
→ Contract
→ Procurement
→ Project
→ Investment
```

第三步：识别收款主体：

```text
Payment
→ Counterparty
→ Supplier
→ Shareholder
→ BeneficialOwner
```

第四步：识别决策责任：

```text
Project
→ Decision
→ Meeting
→ Approval
→ Person
```

第五步：风险判断：

```text
项目完成度 35%
付款比例 97%
```

触发：

```text
Rule：项目进度与付款进度异常
RiskEvent：HIGH
```

第六步：风险闭环：

```text
RiskEvent
→ Clue
→ Investigation
→ Enterprise Explanation
→ Evidence
→ Rectification
→ Review
→ Close
```

这体现了 DRP 的完整技术链路，而不是单纯的数据展示。

# 20. 总结

国资 DRP 的关键不是某一种技术，而是把数据、语义、分析和监管处置组合成一个完整的平台。

可以将整个体系概括为：

```text
数据源
  ↓
数据平台
  ↓
数据治理
  ↓
Ontology 语义中枢
  ↓
Rule / Graph / Risk Model / Search / AI
  ↓
RiskEvent
  ↓
监管闭环
  ↓
穿透监管应用
```

其中：

- **数据平台**回答“事实在哪里”；
- **数据治理**回答“数据是否可信”；
- **Ontology**回答“事实在业务上是什么、彼此有什么关系”；
- **规则和模型**回答“哪里存在风险”；
- **AI Agent**回答“如何理解、查询、解释并组合工具”；
- **风险闭环**回答“发现以后如何处置”；
- **监管应用**回答“监管人员最终如何使用这些能力”。

最终形成：

> **数据可治理、对象可统一、关系可穿透、规则可执行、风险可解释、过程可协同、证据可追溯、整改可闭环、责任可追踪、AI 可安全调用。**

这就是国资 DRP 的总体技术架构和各模块之间的核心关系。
