# 目标

对 `ontology/` 下已挖掘的 SAP FI-AP Ontology 模型做一次**完整的工程级审查**，产出三份可直接执行的结论：
(1) 正确性与一致性缺陷清单；(2) Object Type 补全建议；(3) Action Type 补全建议。

# 背景

- **唯一需求来源**：`docs/SAP_FI-AP(应付账款)模块功能清单.md`（5 大章：后台配置 / 主数据 / 前台业务 / 报表分析 / 周期作业）。
- **被审查物**：`ontology/` 目录，遵循 Palantir Foundry Ontology 建模范式：
  - `00-conventions.md` — 强制建模契约（命名、baseType 白名单、主键策略、状态机、表达式语法）。**契约优先于任何单个文件的写法。**
  - `01-object-type-inventory.md` — 权威范围定义，90 个 Object Type，分 8 个域（D1 凭证内核 → D8 报表期末）。
  - `object-types/<域>/<ApiName>.md` — **唯一事实来源**。每个文件含：概述 / Object Type 定义 / Properties / 状态机 / §5 Link Types / §6 Action Types / 校验规则 / 索引与查询模式 / 未决问题。
  - `interfaces/`、`value-types/`、`link-types/README.md`、`action-types/README.md` — 后两者是 `tools/generate_registries.py` 的**派生产物，不要作为事实来源，也不要直接改**。
- **模型用途**：**不是给业务方看的概念模型，而是重新开发一套 AP 模块的实现蓝图**。读者是要照此写代码的工程师。因此描述可以且应当技术化：字段精度、主键、幂等语义、并发与锁、状态迁移前后置条件、批处理边界、异常与补偿路径，都属于本模型该说清楚的内容。

# 硬性约束

1. **只使用 Opus 5 自身的 SAP FI-AP 领域知识进行校验，禁止联网检索**（不调用 WebSearch / WebFetch）。凡涉及 SAP 标准表结构、事务码、配置语义的判断，直接依据内部知识给出，并在不确定时显式标注置信度（高 / 中 / 低），而非去查。
2. **只读审查，不修改仓库文件**，除非我另行指示。所有产出以报告形式给出。
3. 结论必须**锚定到具体文件与行号**（`ontology/object-types/04-invoice/VendorInvoice.md:132` 形式），禁止泛泛而谈。
4. 区分三类问题，不要混为一谈：**缺陷**（与契约或 SAP 语义冲突，必错）/ **风险**（可实现但会在某场景下出问题）/ **建议**（可选增强）。
5. 覆盖率优先于修辞：宁可条目多而短，不要少而长。

## 四处要判定并修的地方

1. **无域需求的提交数没有归属。**
   app-shell 步 0 与 shared-package 第 1 步那两张分流表,把「改外壳」与「改共享包」
   写成互斥的两支。但外壳只要需要一个新的共享类型或共享组件,真实形状就是顺序的:
   先一个共享包提交(owner 签字、单独 MR),再一个外壳提交。而 app-shell 的产出栏
   写着「一个提交」,它没有任何词汇描述这个形状 —— 于是碰上这种需求时,做法只能
   现场发明。
   判:是给 app-shell 加一个「前置共享包变更」分支,还是让无域路径也能进 slice?
   写出可判定的判据,不许写成「必要时」。

2. **无域路径上有没有计划确认停点,现在的答案是隐式的。**
   停「计划确认」在停点总表里归 slice 第 7 步,而 app-shell 从不调 slice ——
   所以答案实际是「没有」,但没有一句话写着这件事。它的后果是:无域路径可以
   多片连做而从不停,且完全符合技能正文。
   判:不该有,就把这句话连理由显式写进 app-shell;该有,就写清由谁停、停什么、
   停在哪一步之前。

3. **计划文件在无域路径上的地位没定。**
   plan-coverage 的域判定匹配不到 apps/web/app/ 与 libs/shared/,app-shell 与
   shared-package 两份的「挡不住什么」都各自承认这是零信号盲区。
   判:无域改动该不该写计划文件?写了的话,有没有任何东西能验证它写在开工前 ——
   还是说一份开工后补的计划文件,和开工前写的那份在产出上完全无法区分?
   给一个明确答案,不要留给下一次即兴决定。

4. **「回答了澄清问题」与「批准了计划」之间缺一条区分。**
   澄清环问的是每片内部的形态(某个字段怎么落、某个值从哪来),计划确认批准的是
   切成哪几片、什么顺序。前者答完之后继续往下做,看起来像已获授权,而实际上
   没有人看过那个片的列表。
   判:找一处合适的位置把这条区分写下来,并说明它归谁。

## 约束

- 判据只留一份。新增判据要在 CONVENTIONS.md 第一章真源总表里有归属,不要在两份
  技能里各写一遍 —— 那正是「改了一处,另一处静默失效」。
- 委派写成可判定的分支,不写成并列清单;跳过某个分支时要显式说明为什么跳过。
- 优先能变红的机制。贯穿原则是「一条规则失效时的表现,不能和这条规则本来就不适用
  长得一样」:能落成模板仓 tests/ 断言的就落断言,不要只加正文。
  但不要造 marker 式断言 —— 让模型写一句「我确认过了」是可被满足而不被执行的。
- 每份被改的技能,同步更新它的「这份技能挡不住什么」。
- 改完逐条说明:每处改动对应上面四条里的哪一条,以及它失效时会不会变红。

第 3 条和第 4 条是这四条里唯一可能没法落成断言的两条 —— 「写在开工前」和「批准过」都不留物理痕迹。真做的时候大概会收敛成正文加一条停点,那也是诚实的结果,写进「挡不住什么」比硬造一条假绿断言好。
